# Monitoring and Logging Kubernetes Clusters and Apps

In this module, you will learn following:

- How to monitor Kubernetes cluster components and applications?
- How to get the infrastructure-level, system-level, and application-level logs to serve as a source for log analytics or troubleshooting?
- Monitoring applications on a Kubernetes cluster
- Managing logs at the cluster node and pod levels
- Managing container **stdout** and **stderr** logs

## 01. Monitoring Cluster Nodes

### Step-1.1: Check whether _Metrics Server_ is installed or not

```bash
# List all the worker nodes in the cluster
kubectl get nodes

[The preceding command will list all the worker node names. Here, let's assume node name is "minikube"]

# Check the metrics for the worker node (e.g. minikube)
kubectl top node minikube

[ The output of this command will show the resource usage of the minikube node if you have Metrics Server installed]
```

- In case if the Metrics server is not installed on your K8s server, you will the following error

```bash
error: Metrics API not available
```

### Step-1.2: Installing Metrics Server on Kubernetes cluster

- To get the latest release and instructions, you can go to kubernetes gitHub repo: https://github.com/kubernetes-sigs/metrics-server .

#### 1.2.1 Using minikube Addon (on minikube distro)

```bash
# List minikube addons
minikube addons list

# List minikube addons and filter the metrics-server
minikube addons list | grep metrics-server

# Enable metrics-server addon on minikube k8s cluster
minikube addons enable metrics-server

# List the pods and services related to metrics-server
kubectl get pods,svc -n kube-system
OR
kubectl get pods -n kube-system | grep metrics-server
```

#### 1.2.2 Using a YAML manifest file

```bash
# Deploy Metrics server using the official YAML manifest file
kubectl apply -f https://github.com/kubernetes-sigs/metricsserver/releases/latest/download/components.yaml
```

- There is also a high-availability (HA) version that increases the replica count from one to two for Metrics Server.
- If you have a k8s cluster with at least two nodes, you can use the following manifest file for installing metrics-server

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metricsserver/releases/latest/download/high-availability.yaml
```

- To get more information about Metrics Server, follow this link: https://github.com/kubernetessigs/metrics-server/releases

#### 1.2.3 Using Helm Charts

- To install Metrics Server using Helm charts, you can go to [Artifact Hub](https://artifacthub.io/) and then find the Metrics Server Helm charts at https://artifacthub.io/packages/helm/metrics-server/metrics-server

```bash
# Add helm repo for metrics-server
helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/

# Install the Helm charts
helm upgrade --install metrics-server metrics-server/metricsserver
```

## 02. Checking out CPU and Memory metrics

- To get the CPU and memory metrics details of any worker node

```bash
# Syntax
kubectl top node <NODE_NAME>

# Example
kubectl top node minikube
```

## 03. Monitoring Applications on a Kubernetes cluster

- In Kubernetes, the **metrics-server** is not only used to monitor the Kubernetes worker nodes but also the _pods_ and _containers_.

### Step-3.1: Monitoring the resource usage of an application

```bash
# Deploy a test application Pod to monitor it using metrics-server
kubectl run nginx --image=nginx:latest

# Check the resource utilization of the above Pod
kubectl top pod nginx

# Check the resource utilization of multi-container pods
kubectl top pod <POD_NAME> --containers
```

- To show all the metrics of all the Pods across different namespaces, use following command:

```bash
kubectl top pod -A

OR

kubectl top pod --all-namespaces
```

- List the Pods with it's memory and cpu resource utilization details in sorted form

```bash
kubectl top pod --sort-by=cpu

kubectl top pod –-sort-by=memory

[This can help you in figuring out the pods with most/least resource consumption]
```

### Step-3.2: Checking application details

```bash
# Describe a Pod from default namespace
kubectl describe pod <POD_NAME>

# Describe a Pod present in a custom namespace
kubectl describe pod <POD_NAME> -n <NAMESPACE>
```

### Step-3.3: Monitor K8s cluster events

```bash
kubectl get events

# List the events sorted by timestamp
kubectl get events --sort-by=.metadata.creationTimestamp

# To collect the events during a deployment | Real-time logs
kubectl get events --watch
```

### 4.1 Node level details

```bash
# Checking node status
kubectl get node minikube -o wide
```

## 5. Managing container `stdout`, `stdin` and `stderr` logs

```bash
kubectl logs <POD_NAME>
```

- We can get into the pod to retrieve the specific container log by using the **-c flag**.

```bash
kubectl logs <POD_NAME> -c <CONTAINER_NAME>
```

- Stream the logs

```bash
kubectl logs -f <POD_NAME>
```

- List logs generated since xx duration

```bash
# Since last 1 hour
kubectl logs --since=1h
```

## 6. Production-grade Monitoring solution

- There is no single _absolute best_ monitoring solution for production-grade Kubernetes, as the optimal choice depends entirely on your:
  - Team's budget
  - Engineering capacity
  - Data retention requirements
- The industry standard comes down to a choice between two main paths:
  1. The `Prometheus + Grafana` open-source stack for maximum data control, or
  2. A commercial SaaS platform like `Datadog` for turnkey convenience.

| Solution                 | Best For                                           | Architecture / Delivery            | Standout Edge                                                                     |
| ------------------------ | -------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| **Prometheus + Grafana** | Cost control, customization, and vendor-neutrality | Self-hosted or managed open-source | De facto CNCF standard with massive community support and native K8s integration. |

### 6.1 The Industry Standard: `Prometheus + Grafana`

- The combination of Prometheus and Grafana forms the baseline architecture for modern Kubernetes observability.

- _The Blueprint_
  - _Prometheus_ acts as the time-series database pulling metrics via cAdvisor and kube-state-metrics, while _Grafana_ acts as the unified visualization layer.

- _Production Implementation_
  - In production, teams rarely deploy these manually.
  - Usually, they use the _kube-prometheus-stack_ Helm chart, which bundles pre-configured, battle-tested dashboards and alerting rules out of the box.

### 6.2 The Modern Standard: `OpenTelemetry` Instrumentation

### Lab: Deploy a production-ready Prometheus and Grafana stack on Minikube

- To deploy a production-ready Prometheus and Grafana stack on Minikube, the industry standard is to use the `kube-prometheus-stack` Helm chart.
- This bundles _Prometheus_, _Grafana_, _Alertmanager_, and _pre-configured cluster dashboards_ into a single installation.

#### Prerequisites

- Minikube based K8s Cluster running on an EC2 Instance

#### Step-01: Start Minikube

- _Prometheus_ and _Grafana_ require more resources than a default Minikube installation provides.
- Allocate at least 2 CPUs and 3.5GB of RAM.

```bash
minikube start --cpus=2 --memory=4096

# Verify your cluster is up and running
kubectl cluster-info

# Verify the nodes and status
kubectl get nodes
```

#### Step-02: Install `Helm`

```bash
# macOS (Homebrew)
brew install helm

# Linux (Ubuntu/Debian)
sudo apt-get install helm

# Windows (Chocolatey)
choco install kubernetes-helm

# Amazon Linux 2023 - https://helm.sh/docs/intro/install/
curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3

chmod 700 get_helm.sh

./get_helm.sh
```

#### Step-03: Add the `Prometheus` Helm Repository

- Add the official Prometheus community Helm repository to your local system and update it to get the latest charts.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts

helm repo update
```

#### Step-04: Deploy the `Prometheus & Grafana` Stack

```bash
# Create a dedicated namespace called "monitoring" and install the chart in it
kubectl create namespace monitoring

# Install the Prometheus Stack Helm Chart
helm install prometheus-stack prometheus-community/kube-prometheus-stack --namespace monitoring
```

> [!NOTE]
> This step installs Prometheus, Grafana, Alertmanager, node-exporters, and kube-state-metrics which automatically scrapes cluster data.

#### Step-05: Verify the Deployment

- It can take 1–2 minutes for all components to pull their container images and start.

```bash
# Check the status of the pods
kubectl get pods -n monitoring

# Ensure all pods show a status of Running and are ready
```

#### Step-06: Access the Prometheuus and Grafana Dashboard

- Because we have minikube based K8s cluster, we need to forward port of both prometheus and grafana clusterIP service to publish the application on the host system (EC2).

```bash
kubectl port-forward --address 0.0.0.0 svc/prometheus-stack-kube-prom-prometheus 9090:9090 -n monitoring

kubectl port-forward --address 0.0.0.0 svc/prometheus-stack-grafana 8080:80 -n monitoring
```

> [!NOTE]
> You can change the left "9090" port value to whatever port you want to open on your EC2 instance.

#### Step-07: Update Host Machine's (EC2) Security Group

Allow incoming traffic on the port of EC2 instance on which we have forwarded the traffic (i.e. 9090).

- **Rule-1 (Promethues Web UI)**
  - Allow: 9090 from MyIP

- **Rule-2 (Grafana Web UI)**
  - Allow: 8080 from MyIP

> [!WARNING]
> Because `0.0.0.0` opens the listening port to the entire world, anyone who knows your EC2 public IP address could potentially access your Prometheus dashboard. Instead, set the "Source" of your Inbound Rule to `My IP` so that only your specific home or office network can pass through the AWS firewall.

#### Step-08: Access the Prometheus Dashboard

You can now access both the Prometheus and Grafana web UI from your browser using your EC2 Instance's _Public IP address_ / _Public DNS Name_:

```bash
http://<ec2-public-ip>:<prometheus-nodePort>

# Replace <ec2-public-ip> with your EC2 public IPv4 address and <prometheus-nodePort> with the port number from Step-07

# Example - Promethues Web UI
http://142.251.156.4:9090

# Example - Grafana Web UI
http://142.251.156.4:8080

# Grafana defaults | Username: admin | Password: prom-operator
```

> [!IMPORTANT]
> If you a kubeadm or managed kubernetes cluster, you can use a `LoadBalancer service` or `Ingress` instead.
