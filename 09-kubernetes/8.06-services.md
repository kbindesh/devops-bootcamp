# Kubernetes Services

- A Kubernetes **Service** is an API abstraction that exposes a network application running on one or more Pods behind a single, stable IP address and DNS name.
- Because Pods are temporary and get a new IP address every time they restart or scale, a **Service** provides a permanent front door that automatically routes and load-balances traffic to healthy Pods.

## 01. How Kubernetes Services Work?

Services decouple the frontend clients from the backend Pods using a few key mechanisms:

- **Label Selectors**
  - A Service uses key-value labels (such as app: web) to find and group the specific Pods it should route traffic to.

- **EndpointSlices**
  - Kubernetes automatically creates and updates `EndpointSlice` objects to track the exact IP addresses of healthy, ready Pods matching the Service selector.

- **Service Discovery**
  - Cluster DNS (CoreDNS) automatically assigns the Service a predictable internal domain name formatted as `<service-name>.<namespace>.svc.cluster.local`.

- **Traffic Routing**
  - A network proxy (kube-proxy) runs on every node and updates kernel rules (iptables or IPVS) to intercept traffic sent to the Service IP and forward it evenly to the backend Pods.

## 02. Types of Kubernetes Services

You can configure different _Service_ types depending on whether your application needs internal communication or external internet access.

1. **ClusterIP Service**

2. **NodePort Service**
3. **LoadBalancer Service**
4. **ExternalName**

| Service Type                   | Accessibility         | How It Works                                                                                                   | Primary Use Case                                                                                      |
| ------------------------------ | --------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **ClusterIP (Default)**        | Internal only         | Assigns a virtual IP reachable only from inside the cluster.                                                   | Communication between internal microservices (e.g., frontend talking to a backend API).               |
| **NodePort**                   | External and internal | Opens a static port (range 30000–32767) on every worker node's IP address and routes traffic to a ClusterIP.   | Quick testing, demos, or bare-metal clusters without a cloud load balancer.                           |
| **LoadBalancer**               | External and internal | Integrates with your cloud provider (AWS, GCP, Azure) to provision an external load balancer with a public IP. | Exposing production applications directly to public internet traffic.                                 |
| **ExternalName**               | Internal to external  | Maps the Service name to an external DNS address using a CNAME record without any proxying.                    | Allowing Pods to connect to external databases or third-party APIs using a local cluster name.        |
| **Headless (clusterIP: None)** | Internal only         | Bypasses load balancing and virtual IPs, returning the individual IP addresses of all matching Pods via DNS.   | Stateful applications (like databases or Kafka) where clients need to talk to specific Pods directly. |

## 03. Lab: Deploy an Application & publish it using _ClusterIP_ service within cluster

Here is a ClusterIP Service example featuring an Nginx backend application and a temporary client Pod to verify internal DNS resolution and traffic routing.

### Step-3.1: Application Deployment and ClusterIP Service

- Save the following manifest as `clusterip-demo.yaml`.
- It creates a 2-replica Nginx application labeled `app: backend-web` and exposes it internally on port 8080.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend-web
  template:
    metadata:
      labels:
        app: backend-web
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  type: ClusterIP
  selector:
    app: backend-web
  ports:
    - protocol: TCP
      port: 8080 # Port other pods use to call this Service
      targetPort: 80 # Port the Nginx container listens on
```

- Apply the manifest and confirm the Service has received a cluster-internal IP address:

```bash
kubectl apply -f clusterip-demo.yaml

kubectl get svc backend-service
```

### Step-3.2: Run a Test Pod to Verify Connectivity

- Launch an ephemeral curl Pod inside the cluster to test reaching the Service using its DNS name (backend-service) and port (8080).

- Because ClusterIP is internal-only, this request will succeed from inside the cluster while remaining unreachable from your local machine.

```bash
kubectl run test-client --image=curlimages/curl --rm -it --restart=Never -- curl -I http://backend-service:8080
```

- **Expected Output**
  - You should receive an HTTP/1.1 200 OK header response from Nginx, and Kubernetes will automatically delete test-client as soon as the command finishes (--rm).

- **Troubleshooting Tip**
  - If the request hangs or fails, run `kubectl get endpointslices -l kubernetes.io/service-name=backend-service` to verify that the Pod IP addresses are listed and match the _app: backend-web_ selector.

### Step-3.3: Clean-up Resources

- Once you finish testing, remove the Deployment and Service:

```bash
kubectl delete -f clusterip-demo.yaml
```

## 04. Lab: Deploy an Application & publish it on the web using _LoadBalancer_ Service

To expose the same above `backend-app` Deployment publicly on Amazon EKS, change the _Service_ type to **LoadBalancer** and add _AWS annotations_ so EKS provisions an internet-facing AWS Network Load Balancer (NLB).

### Step-4.1: Prerequisites

- An Amazon EKS cluster with atleast one worker node

### Step-4.2: Update the Service to _LoadBalancer_

- Save the following K8s manifest as `eks-loadbalancer-demo.yaml` and apply it.
- If your cluster uses the AWS Load Balancer Controller or EKS Auto Mode, the annotations below direct AWS to route traffic straight to your Pod IPs.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend-web
  template:
    metadata:
      labels:
        app: backend-web
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: backend-service
  annotations:
    # Provisions a modern AWS Network Load Balancer (NLB)
    service.beta.kubernetes.io/aws-load-balancer-type: "external"
    # Routes traffic directly to Pod IPs (requires VPC CNI / AWS Load Balancer Controller)
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: "ip"
    # Makes the NLB publicly accessible from the internet
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
spec:
  type: LoadBalancer
  selector:
    app: backend-web
  ports:
    - protocol: TCP
      port: 80 # Public port exposed on the AWS NLB
      targetPort: 80 # Port the Nginx container listens on
```

> [!NOTE]
> If you have not installed the AWS Load Balancer Controller and are not using EKS Auto Mode, omit the _annotations_ block - EKS will still provision a default load balancer, though AWS recommends the _controller_ for production workloads.

- Apply the updated manifest:

```bash
kubectl apply -f eks-loadbalancer-demo.yaml
```

### Step-4.3: Get the External AWS DNS Name

- It will take ~3 minutes to provision the AWS Network Load Balancer and register your Pods.
- Watch the Service until **EXTERNAL-IP** changes from `<pending>` to an `*.elb.<region>.amazonaws.com` hostname:

```bash
kubectl get svc backend-service -w
```

### Step-4.4: Test From Your Local Machine

- Unlike ClusterIP, you do not need a test Pod inside the cluster anymore.

- Once the EXTERNAL-IP appears, test the public endpoint directly from your local terminal or web browser:

```bash
curl -I http://<YOUR-NLB-EXTERNAL-DNS>
```

- **Expected Output**
  - An HTTP/1.1 200 OK response from Nginx served over the public internet.

- **EKS Troubleshooting Tip**
  - If the external URL times out after 3+ minutes, verify that your VPC's public subnets are tagged with `kubernetes.io/role/elb = 1`, which AWS requires to place an internet-facing load balancer.

### Clean-up Resources

- Once you finish testing, remove the Deployment and Service:

```bash
kubectl delete -f eks-loadbalancer-demo.yaml
```
