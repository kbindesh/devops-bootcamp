# Terraform Key Concepts

**1. Terraform Configuration files & Directories**

- Terraform processes all configuration files in a single directory as a single module (the root module).
- _Standard File Extensions_
  - **.tf**: The standard extension for configuration files containing top-level blocks.

  - **.tfvars**: Used strictly to assign values to input variables (e.g., db_port = 5432).
  - **.tfstate**: The JSON file generated by Terraform to track infrastructure state. Never edit this manually.
  - **terraform.tfstate.backup**
    - It is an automatically generated snapshot of your previous Terraform state (terraform.tfstate).
    - It acts as a safety net, capturing the last known good configuration before Terraform makes any destructive or modifying changes during operations like _terraform apply_.

  - **.terraform/**
    - This directory acts as a local cache. It stores downloaded provider plugins and remote module code.
    - It is completely ephemeral and should always be added to your .gitignore file.
  - **.terraform.lock.hcl**
    - The dependency lock file. Created during terraform init, it records the exact versions and cryptographic hashes of the providers used.
    - Commit this to version control to guarantee consistent builds across teams.

**2. Terraform top-level blocks**

- Terraform configuration files consist of top-level blocks.
- These are the primary structural building blocks used to define infrastructure, configure settings, and manage variables.

## Terraform Top-level Blocks

- **terraform**
  - Configures Terraform settings, including the required version, required provider versions, and the state backend.
- **provider**
  - Specifies the cloud or service platform (like AWS or Azure) and its authentication details.
- **resource**
  - Defines a piece of infrastructure to be created and managed, such as a virtual machine or database.
- **data**
  - Reads information from external resources or existing infrastructure outside the current Terraform workspace.
- **variable**
  - Declares input variables to make your configuration reusable, flexible, and dynamic.
- **output**
  - Defines values that Terraform will display on the command line or pass to other configurations after an application.
- **module**
  - Instantiates a self-contained package of Terraform configurations from local files or remote registries.
- **locals**
  - Defines local names and expressions that can be reused multiple times within the same module to avoid repetition.
- **moved**
  - Records when a resource has been renamed or moved within your code, preventing Terraform from destroying and recreating it.

## Recommended Root Directory Layout

### Directory Layout for Standard Projects

- For a standard project, the HashiCorp community recommends breaking your top-level blocks into separate files rather than writing one massive file.
- Terraform merges all `.tf` files in the directory at runtime, so file names do not change execution logic—they are purely for human organization.

```bash
my-terraform-project/
├── main.tf          # Core infrastructure resources and data sources
├── providers.tf     # terraform {} settings and provider configurations
├── variables.tf     # variable {} block declarations (no values assigned)
├── outputs.tf       # output {} blocks defining post-apply visibility
├── locals.tf        # locals {} block for calculated internal variables
├── terraform.tfvars # Default values for variables (automatically loaded)
└── .terraform/      # Hidden directory created by 'terraform init' (gitignored)
```

### Directory Design-patterns for Multi-Environment setup

- To manage multiple environments (like Dev, Staging, and Production), you must separate your configurations to prevent accidental overlaps.
- There are two primary directory design patterns used in the industry:
  1. The Directory Separation Pattern (most Common)
  2. The .tfvars File Separation Pattern

#### The Directory Separation Pattern

- You create dedicated folders for each environment, with each folder calling reusable modules.
- This keeps environments completely isolated and secure.

```bash
environments/
├── modules/
│   └── web_app/
│       ├── main.tf
│       └── variables.tf
├── dev/
│   ├── main.tf      # Calls modules/web_app with dev variables
│   └── providers.tf
└── prod/
    ├── main.tf      # Calls modules/web_app with prod variables
    └── providers.tf
```

#### The .tfvars File Separation Pattern

- You use a single set of .tf files, but switch environments by passing a specific variables file during execution (e.g., terraform apply -var-file=prod.tfvars).

```bash
my-terraform-project/
├── main.tf
├── variables.tf
├── dev.tfvars       # Dev-specific environment values
└── prod.tfvars      # Prod-specific environment values
```
