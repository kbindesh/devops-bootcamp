# Jenkins Pipeline

## What is a Jenkins Pipeline?

- A Jenkins Pipeline is a suite of plugins that supports implementing and integrating continuous delivery pipelines into Jenkins.
- It provides an automated way to define your entire build, test, and deployment lifecycle as code, typically stored in a text file named a `Jenkinsfile`.
- Instead of manually creating and clicking through web forms in the Jenkins UI to configure a job, you write out the sequence of steps. This concept is widely known as _Pipeline-as-Code_.

### Jenkins Pipeline Core concepts

- **Jenkinsfile**
  - A plain text file containing your pipeline definition that you commit directly to your application's source control repository (like GitHub, GitLab, or Bitbucket).
- **Pipeline as Code**
  - Because your build configuration is in your repository, it is version-controlled, can be peer-reviewed via pull requests, and can be tracked just like application code.
- **Durable & Resilient**
  - Jenkins pipelines are designed to survive both planned and unplanned restarts of the Jenkins controller.
  - If Jenkins reboots midway through a long build, the pipeline can pick up right where it left off.
- **Visual Feedback**
  - Pipelines provide an explicit, chronological step-by-step visual map (Stage View) in the Jenkins UI, making it instantly clear exactly where a build failed.

### Scripted vs Declarative Pipeline

- Jenkins offers two distinct styles for writing a pipeline, namely:
  1. Declarative Pipeline
  2. Scripted Pipeline
- While they run on the same underlying engine, their syntax models are completely different:

#### 1. Declarative Pipeline (recommended)

- This is a modern, rigid, and structured format.
- It provides an opinionated framework with predefined blocks (pipeline, agent, stages, steps) making it highly readable and incredibly easy to write for most of standard CI/CD workflows.

  ```groovy
  pipeline {
      agent any
      stages {
          stage('Build') {
              steps {
                  echo 'Building application...'
              }
          }
      }
  }
  ```

#### 2. Scripted Pipeline (Legacy/Advanced)

- This is an imperative, free-form format based directly on Groovy programming logic.
- It offers maximum flexibility and power but demands a much steeper learning curve because you must handle your own error catching, conditional routing, and block structures.

  ```groovy
  node('optional-node-label') {
      stage('Example Stage') {
          // Raw commands go directly here
          echo 'Executing logic directly inside the stage closure'
      }
  }
  ```

## Jenkins Pipeline (Declarative) - Syntax

### 01. Pipeline

- A Jenkins Declarative Pipeline uses a structured, opinionated Groovy DSL encapsulated within a mandatory `pipeline {}` block.
- It provides a standardized, human-readable format for building CI/CD workflows, making error prevention and maintenance significantly easier than traditional scripted syntax.

```groovy
pipeline {
    /*
       1. AGENT (Mandatory)
       Defines where the pipeline execution occurs.
       Options: 'any', 'none' (set agent per stage), or specific labels.
    */
    agent any

    /*
       2. OPTIONS (Optional but highly recommended)
       Configures properties for the entire pipeline.
    */
    options {
        timeout(time: 1, unit: 'HOURS') // Aborts the build if it hangs
        retry(2)                        // Retries the pipeline on failure
        timestamps()                    // Adds timestamps to console logs
    }

    /*
       3. PARAMETERS (Optional)
       Defines variables users must input when manually running the build.
    */
    parameters {
        string(name: 'BUILD_ENV', defaultValue: 'staging', description: 'Target environment')
        booleanParam(name: 'RUN_SONAR', defaultValue: true, description: 'Run code analysis')
    }

    /*
       4. ENVIRONMENT (Optional)
       Defines global environment variables or securely injects credentials.
    */
    environment {
        APP_NAME     = 'my-microservice'
        REGISTRY_URL = 'docker.io/mycompany'
        DB_PASSWORD  = credentials('database-secret-id') // Secure credential injection
    }

    /*
       5. STAGES (Mandatory)
       The main wrapper that contains all individual execution phases.
    */
    stages {

        /*
           6. STAGE (Mandatory - At least one required)
           Represents a single conceptual phase of your CI/CD workflow.
        */
        stage('Checkout & Initialize') {
            /*
               7. STEPS (Mandatory inside each stage)
               Defines the actual commands or tasks executed in this stage.
            */
            steps {
                echo "Initializing deployment for ${APP_NAME}..."
                git branch: 'main', url: 'https://github.com'
            }
        }

        stage('Code Analysis') {
            /*
               8. WHEN (Optional)
               Enforces conditional execution for this specific stage.
            */
            when {
                environment name: 'RUN_SONAR', value: 'true'
            }
            steps {
                echo "Running SonarQube quality gate..."
                // sh './gradlew sonarqube'
            }
        }

        stage('Build & Test') {
            /*
               9. PARALLEL (Optional)
               Runs multiple isolated sub-stages concurrently to save execution time.
            */
            parallel {
                stage('Unit Tests') {
                    steps {
                        sh 'echo "Running backend unit tests..."'
                    }
                }
                stage('Frontend Linters') {
                    steps {
                        sh 'echo "Running frontend code linters..."'
                    }
                }
            }
        }

        stage('Deploy') {
            steps {
                /*
                   10. SCRIPT (Optional)
                   Escapes declarative rules to run flexible, imperative Groovy logic.
                */
                script {
                    if (params.BUILD_ENV == 'production') {
                        echo "Triggering Production deployments..."
                    } else {
                        echo "Deploying strictly to Staging environments..."
                    }
                }
            }
        }
    }

    /*
       11. POST (Optional but foundational)
       Executes cleanup, notifications, or logging blocks based on build outcome.
    */
    post {
        always {
            echo 'Executing cleanup tasks...'
            deleteDir() // Cleans the active workspace
        }
        success {
            echo 'Pipeline completed perfectly!'
        }
        failure {
            echo 'Pipeline execution broke. Alerting team via notifications...'
        }
    }
}
```

### 02. Pipeline Sections

#### 2.1 agent

- **top-level agent**

  ```groovy
  pipeline {
      agent any
      stages {
          stage('stage_label') {
              steps {
                  echo 'Hello there'
              }
          }
      }
  }
  ```

- **stage-level agent**

  ```groovy
  pipeline {

      agent none

      stages {
          stage('stage_label') {
              agent any
              steps {
                  echo 'Hello World'
              }
          }
      }
  }
  ```

The agent section parameters are as follows:

1. **any**
   - Execute the Pipeline, or stage, on any available _agent_ (aka slave or node).
   - For example: `agent any`
2. **none**
   - Is applied at the top-level of the pipeline block.
   - No global agent will be allocated for the entire Pipeline run and each stage section will need to contain its own agent section.
   - For example: `agent none`
3. **label**
   - Execute the Pipeline, or stage, on an agent available in the Jenkins environment with the provided label.
   - For example: `agent { label 'my-defined-label' }`

4. **node**

- In a Jenkins Declarative Pipeline, configuring the **agent** as a **node** allows you to explicitly target specific build servers (agents/slaves) or control exactly where a workspace is allocated using labels or custom parameters.

- By default, writing agent any lets Jenkins pick any available worker.
- Using agent { node { ... } } gives you granular control over the build environment.

  ```groovy
  agent {
      node {
          label 'my-target-node-label'
          customWorkspace '/var/jenkins_workspaces/my-app' // Optional
      }
  }
  ```

5. **docker**
   - Execute the Pipeline, or stage, within the given container which will be dynamically created on a node.

   ```groovy
   agent {
      docker {
          image 'maven:latest'
          args  '-v /tmp:/tmp'
          registryUrl 'https://myregistry.com/'
          registryCredentialsId 'myPredefinedCredentialsInJenkins'
      }
    }
   ```

#### 2.2 tools

- Defines the tools or build environment to be used in the pipeline.
- Supported Tools
  - maven
  - jdk
  - gradle

  ```groovy
  pipeline {
      agent any
      tools {
          maven 'maven-3.9.11'      // The tool name must be defined in Jenkins under Manage Jenkins → Tools
      }

      stages {
          stage('Get Maven Version') {
              steps {
                  sh 'mvn --version'
              }
          }
      }
  }
  ```

#### 2.3 stages

- The stages section may contain one or more than one stage directives (sub-section).
- The stage section defines the real tasks to be carried out by the Jenkins pipeline.
- **Recommendation**
  - Have at least one stage directive for each discrete part of the continuous delivery (CD) process such as:
    1. Build
    2. Test
    3. Deploy

  ```groovy
  pipeline {
      agent any
      stages {
          stage('Build App') {
              steps {
                  echo 'Building the App'
              }
          }
          stage('Unit Test App') {
              steps {
                  echo 'Test the App'
              }
          }
          stage('Deploy App') {
              steps {
                  echo 'Deploying the App'
              }
          }
      }
  }
  ```

#### 2.4 post

- The post section defines one or more additional steps that you want to run upon the successful completion of a jenkins pipelines or stage's run.
- You can add the _post_ section in the outer-most _pipeline_ block or inside a particular _stage_ block.
- **Conditions**: _always, changed, fixed, aborted, failure, success, failure, unsuccessful, unstable._

  ```groovy
  pipeline {
      agent any
      stages {
          stage('stage_label') {
              steps {
                  echo 'Hello there'
              }
          }
      }
      post {
          always {            // Post condition
              echo 'I will always say Hello!'
          }
      }
  }
  ```

- **always**: Runs regardless of the final status.
- **success**: Runs only when the pipeline or stage concludes successfully.
- **failure**: Executes if the current state breaks.
- **unstable**: Executes if tests break or code metrics fail but the build continues.
- **changed**: Fires only if the resulting status differs from the immediate previous run.

### 03. Directives

#### 3.1 environment

- Environment variables are key-value pairs that store configuration settings, credentials, and other dynamic values used during build and deployment processes.
- Environment variables can be defined at various levels, including:
  - system-wide (Jenkins global settings)
  - per-node
  - per-job
  - within pipeline scripts
- You can define custom environment variables using _Jenkins UI_, _env_ directive in pipelines, or _external configuration files_.

```groovy
// Setting local environment variables in declarative pipelines

pipeline {
    agent any
    environment {       // pipline-level env variable; accessible to all stages
        HELLO = 'WORLD'
    }
    stages {
        stage('Morning') {
            environment {           // stage specific env var
                GREETING = 'Good morning!'
            }
            steps {
                echo env.HELLO
                echo env.GREETING
            }
        }
        stage('Evening') {
            steps {
                echo env.HELLO
                echo env.GREETING     // This is invalid as GREETING env is defined in another stage
            }
        }
    }
}

```

- Some of the `Jenkins built-in environment variables` are as follows:
  - BUILD_NUMBER
  - JOB_NAME
  - BUILD_URL
  - NODE_NAME
  - WORKSPACE

- **Storing sensitive information in environment variables**

```groovy
// To use an existing jenkins credential in a Jenkins pipeline, you can use "credentials" directive within environment block

pipeline {
    agent any
    environment { // accessible to all stages
        HELLO = 'WORLD'
        MY_SECRET = credentials("MY_SECRET_MSG") // credentials directive | pass credential ID as param
    }
    stages {
        stage('Morning') {
            environment {
                GREETING = 'Good morning!'
            }
            steps {
                echo env.HELLO
                echo env.GREETING
                echo env.MY_SECRET      // prints secret text
            }
        }
        stage('Afternoon') {
            steps {
                echo env.HELLO
                echo env.GREETING       // This is invalid as GREETING env is defined in another stage
            }
        }
    }
}
```

- To view Jenkins environment variables list:
  - via _web browser_: `[Jenkins URL]/env-vars.html`
  - via shell command in a Jenkins job: steps { bat 'set' // for windows }

#### 3.2 parameters

- _parameter_ directive provides a list of parameters which you can define in the jenkinsfile.
- Each parameter has a Name and Value.
- Use _params_ object to access defined parameters in the pipeline.
- Parameter Types
  - string
  - text
  - booleanParam
  - choice
  - password

  ```groovy
  pipeline {
      agent any
      parameters {
          string(name: 'PERSON', defaultValue: 'Mr Jenkins', description: 'Who should I say hello to?')

          text(name: 'BIOGRAPHY', defaultValue: '', description: 'Enter some information about the person')

          booleanParam(name: 'TOGGLE', defaultValue: true, description: 'Toggle this value')

          choice(name: 'CHOICE', choices: ['One', 'Two', 'Three'], description: 'Pick something')

          password(name: 'PASSWORD', defaultValue: 'SECRET', description: 'Enter a password')
      }
      stages {
          stage('Example') {
              steps {
                  echo "Hello ${params.PERSON}"

                  echo "Biography: ${params.BIOGRAPHY}"

                  echo "Toggle: ${params.TOGGLE}"

                  echo "Choice: ${params.CHOICE}"

                  echo "Password: ${params.PASSWORD}"
              }
          }
      }
  }
  ```

#### 3.3 input

- The _input_ directive on a stage allows you to prompt for getting input value from the user.
- The stage will pause after any options have been applied, and before entering the agent block for that stage or evaluating the when condition of the stage.
- If the input is approved, the stage will then continue.

- _Configuration options_: message, id, ok, submitter, parameters

  ```groovy
  pipeline {
      agent any
      stages {
          stage('Example') {
              input {
                  message "Should we continue?"
                  ok "Yes, we should."
                  submitter "alice,bob"
                  parameters {
                      string(name: 'PERSON', defaultValue: 'Mr Jenkins', description: 'Who should I say hello to?')
                  }
              }
              steps {
                  echo "Hello, ${PERSON}, nice to meet you."
              }
          }
      }
  }
  ```

#### 3.4 when

- The _when_ directive allows the Pipeline to execute a stage conditionally.
- The when directive must contain at least one condition.

  ```groovy
  pipeline {
      agent any
      stages {
          stage('Build App') {
              steps {
                  echo 'Hello World'
              }
          }
          stage('Deploy App') {
              when {
                  branch 'production'
              }
              steps {
                  echo 'Deploying'
              }
          }
      }
  }
  ```

### 04. Sequential Stages

- In a Jenkins Declarative Pipeline, `Sequential Stages` allow you to group a series of child stages to execute in a strict, step-by-step chronological order under a parent stage.

- This block structure is highly useful for organizing complex workflows (like multi-tiered testing or phased deployments) while sharing common configurations such as:
  - an agent
  - environment variables, or
  - conditional _when_ statements - across all the nested child stages.

```groovy
pipeline {
    agent any

    stages {
        stage('Build Artifacts') {
            steps {
                echo 'Compiling source code and building application package...'
                sh 'echo "App Built" > build_status.txt'
            }
        }

        /*
           PARENT STAGE: Groups the entire Staging lifecycle.
           The environment variable and conditional check apply to ALL nested stages.
        */
        stage('Staging Gate') {
            when {
                branch 'main' // This entire group only runs on the main branch
            }
            environment {
                TARGET_HOST = '://example.com'
            }

            // Nested block containing the sequential child stages
            stages {
                stage('Deploy to Staging Server') {
                    steps {
                        echo "Deploying built package to ${TARGET_HOST}..."
                        sh 'sleep 3' // Simulating deployment time
                    }
                }

                stage('Execute Component Sanity') {
                    steps {
                        echo "Verifying server endpoints on ${TARGET_HOST}..."
                        sh 'echo "Ping Success"'
                    }
                }

                stage('Run Automated Integration Suite') {
                    steps {
                        echo "Running end-to-end integration test suites against Staging..."
                        sh 'sleep 5' // Simulating test execution
                    }
                }
            }
        }

        stage('Production Approval Promotion') {
            steps {
                echo 'Awaiting manual gates for Production release...'
            }
        }
    }
}
```

### 05. Parallel Stages

- Executes non-dependent stages concurrently on different available nodes to minimize build durations:

```groovy
stage('Run Tests Across Browsers') {
    parallel {
        stage('Chrome Suite') {
            steps { sh './run-chrome.sh' }
        }
        stage('Firefox Suite') {
            steps { sh './run-firefox.sh' }
        }
    }
}
```
