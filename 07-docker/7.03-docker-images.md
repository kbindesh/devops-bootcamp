## 01. What are `Docker Images`?

- A **Docker image** is a read-only template that contains a set of instructions for creating a container that can run on the Docker platform.

- It provides a convenient way to package up applications and preconfigured server environments, which you can use for your own private use or share publicly with other Docker users.
- A Docker image is made up of a collection of files that bundle together all the essentials, such as:
  - Installations
  - Application code
  - Dependencies – required to configure a fully operational container environment.

### 1.1 The `Layered Filesystem` of Docker Image

- Container images are templates from which containers are created.
- These images are not made up of just one monolithic block but are composed of many layers.
- The first layer in the image is also called the **base layer**.
- Each layer contains some files and folders.
- Each layer only contains the changes to the filesystem concerning the underlying layers.
- The **layers of a container image are all immutable**. Hence, once generated, the layer cannot ever be changed.

## 02. What is `Docker Build Context`?

- The `Docker Build Context` is the set of local files and directories that the Docker engine can access during the image building process.
- When you run `docker build .` command , the "." specifies that your current working directory is the build context.

1.  Local Context
2.  Remote Context

### 2.1 How Docker Build Context Works?

- Any files you want to include in your image using `COPY` or `ADD` instructions in your _Dockerfile_ must exist within this context.

- Build Context Path or URL
  - You can provide a local directory path, a Git repository URL, or even a remote tarball as the context.

- Traditionally, the entire context is packaged and sent to the Docker daemon (the engine doing the building).
- Newer Docker BuildKit optimizations allow the engine to request only the specific files it needs as it reaches each step.
- For security and predictability, a _Dockerfile_ cannot access files outside of its build context (e.g., you cannot COPY ../secret.txt /).

- Multiple Contexts
  - Modern Docker versions allow you to define multiple named contexts, letting you pull files from different locations into a single build.

## 04. `Dockerfile` file

A _Dockerfile_ is a plain text file containing a sequential list of instructions used to automatically build a Docker image.

Here is a comprehensive breakdown of the most common Dockerfile instructions, ordered by how they typically appear in a file:

- **FROM**
  - Sets the base image for the subsequent instructions.
  - Every valid _Dockerfile_ must start with this instruction.
  - Example: `FROM python:3.11-slim`

- **ARG**
  - Defines variables that users can pass at build-time using `docker build --build-arg <varname>=<value>`.
  - It is the only instruction that can precede `FROM` instruction.
  - Example: `ARG VERSION=latest`

- **LABEL**
  - Adds custom metadata to your image via key-value pairs.
  - Example: maintainer, version, or description

- **WORKDIR**
  - Sets the working directory for any subsequent RUN, CMD, ENTRYPOINT, COPY, and ADD instructions.
  - It creates the directory if it does not exist.
  - Example: `WORKDIR /usr/src/app`

- **ENV**
  - Sets persistent environment variables available during both the build phase and when the container is actively running

- **EXPOSE**
  - Documents the specific network port the container intendedly listens on at runtime.
  - Example: `EXPOSE 8080`
- **COPY**
  - Assigns local files or directories from your host machine and clones them directly into the container's filesystem.
  - Example: `COPY . .`

- **ADD**
  - Functions similarly to COPY, but includes extra capabilities like unpacking compressed .tar files automatically or downloading files directly from remote URLs.
- **RUN**
  - Executes a command terminal script during the build process to add layers, update systems, or install package dependencies.
- **CMD**
  - Specifies the default command and arguments to trigger only when the container initializes.
  - Command-line parameters passed during docker run will completely override this.
- **ENTRYPOINT**
  - Configures the container to run as an unyielding executable.
  - Unlike CMD, it cannot be easily overridden without explicit CLI flags.

## 05. `.dockerignore` file

- A `.dockerignore` file is a configuration file that explicitly defines which files and directories Docker should exclude from the build context.

- It works exactly like a _.gitignore_ file, helping to drastically reduce image sizes, speed up build times, and protect sensitive credentials from leaking into production.

### 5.1 Why you need `.dockerignore` file?

- Faster Builds
- Smaller Images
- Enhanced Security
- Optimal Caching

### 5.2 Location and Syntax

Place the file named exactly `.dockerignore` into the root directory of your build context (usually alongside your Dockerfile).

It uses simple pattern matching:

- "#": Starts a comment line._/temp_ — Excludes files or folders starting with "temp" in any first-level subdirectory.

- \*.log: Excludes any file ending with the .log extension.

- !README.md: An exclamation mark creates an exception, forcing Docker to include the file even if a broader rule excludes it.

## 06. Lab: Containerize an Application using Docker (using Dockerfile)

### Step-6.1: Develop an Application

- For this lab, you can clone a sample [Python Flask Application](https://github.com/kbindesh/python-flask-app.git) GitHub repository on your Docker Host machine:

```bash
# (Optional) In case you do not have Git installed, Install the Git first

ls

```

### Step-6.2: Create a '.dockerignore' file

- Before creating the Dockerfile, add a `.dockerignore` file in your project's root folder.
- This prevents massive or sensitive files (like local dependencies and logs) from being copied into your image, speeding up build times.

```bash
# Git

.gitignore

# Python caching and compiled files
__pycache__/
*.pyc
*.pyo
*.pyd
.pytest_cache/
.ipynb_checkpoints/

# Virtual environments

# Environment variables and secrets (Never bake these into your image!)

# IDEs and Editors

.idea/
*.swp
*.swo

# Docker specific
Dockerfile
docker-compose.yml

# Logs and databases
*.log
instance/
*.db
*.sqlite
```

### Step-6.3: Create a `Dockerfile` file

- Create a file named exactly `Dockerfile` (with no file extension) in your project's root directory.
- Add the following structured instructions into the _Dockerfile_:

```bash
FROM python:3.11-alpine
LABEL maintainer="k.bindesh@gmail.com"
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
EXPOSE 8080
ENTRYPOINT ["python"]
CMD ["src/app.py"]
```

### Step-6.4: Package an Application into Docker Image

- Open your terminal, navigate to your project root, and execute the build command.
- Replace _my-flask-app:v1_ with your desired image name and tag.

```bash
docker image build -t my-flask-app:v1 .

# The . at the very end tells Docker to look for the Dockerfile in the current directory

# Once App is packaged into Docker Image, verify it by listing all the images
docker image ls
OR
docker images

# You should see the image we just created in the prev step
```

### Step-6.5: Deploy Application (Container)

- Once the build completes successfully, deploy the application as a container instance using the following command:

```bash
docker run -dit -p 4001:8080 --name flask-app-c my-flask-app:v1

# View running containers
docker container ls
OR
docker ps

# Inspect or describe container
docker container inspect $CONTAINER_NAME

# View app container logs
docker container logs $CONTAINER_NAME
```

- Command flags/options breakdown:
  - **-d**: Runs the container in "detached" mode, freeing up your terminal screen.
  - **-p 8080:3000**: Maps port 8080 on your host machine to port 3000 inside the container. You can now access your application locally by visiting http://localhost:8080.
  - **-name**: Assigns a recognizable name to your running container instance.

## 07. What is Docker Registry (DockerHub)?

- A Docker registry is a centralized storage and distribution system used to host, manage, and share Docker container images.

- Think of it as a secure app store or a version-control repository (like GitHub) but specifically built for containerized software blueprints.

### 7.1 How It Works?

- **Pushing Images**
  - Developers build a Docker image locally and upload (docker push) it to the registry.
- **Pulling Images**
  - Servers, CI/CD pipelines, or other developers download (docker pull) the image to run it.

- **Organized by Repositories**
  - Within a registry, images are grouped into "repositories" (folders), with each version differentiated by a "tag" (e.g., ubuntu:22.04).

### 7.2 Types of Docker Registries

- **Public Registries**
  - Accessible to anyone globally.
  - ⁠Docker Hub: The default and largest public registry in the world

- **Third-Party & Cloud Registries**
  - Fully managed services hosted by major cloud providers.
  - Amazon ECR (Elastic Container Registry)⁠
  - Google Artifact Registry
  - ⁠Azure Container Registry

- **Private / Self-Hosted Registries**
  - Set up internally by companies behind firewalls to secure proprietary code.
  - Docker Registry (v2): Docker's own basic, open-source server application (registry:2) to run your own local registry instance.
  - ⁠Harbor: An open-source, enterprise-grade private registry.

## 08. Lab: Push the Containerized App (image) to Registry (DockerHub)

### Step-8.1: Prerequisites

### Step-8.2: Create a Docker Hub Account

- Navigate to https://hub.docker.com/

  - Email

- Click **Sign up**
- To verify, sign-in to Docker Hub with above credentials.

### Step-8.3: Log In to Docker Hub from Docker Host using PAT

#### 8.3.1 Generate Docker Hub PAT

Personal Access Tokens (PAT) can be scoped to specific permissions — such as _Read-Only_ for a production server that only pulls images, or _Read/Write_ for a CI/CD build node.

1. Open your browser and log into Docker Hub
2. Click your avatar / profile icon in the top-right corner &rarr; **Account settings**
3. Click on **Personal access tokens** (or Security) in the left sidebar.
4. Click the Generate new token (or New Access Token) button:
   - **Description**: Give it a name (e.g., "Terminal Login" or "CI-CD Pipeline").
   - **Access permissions**: Choose Read, Write, Delete for full CLI access, or Read-only if you only intend to pull images.
   - **Expiration date**: Set a duration based on your security preferences.

- Click **Generate**
- Copy and safe-keep the token immediately. You cannot view it again once you close this screen.

#### 8.3.2 Save the Docker PAT securely on Docker Host

Instead of hardcoding the secret, you can keep the token in a separate, highly restricted file and read it into the variable dynamically when the terminal opens.

```bash
# Save the token in a hidden file
echo "your_actual_token_here" > ~/.docker_token

# Restrict file permissions so only your user can read or write to it
chmod 600 ~/.docker_token

# Load it into the variable via your ~/.bashrc
vi ~/.bashrc

# Add this line to the bottom
export DOCKER_ACCESS_TOKEN=$(cat ~/.docker_token)

# Apply changes
source ~/.bashrc
```

#### 8.3.3 Login to Docker Hub (registry)

Once the variable is loaded, you can log into Docker securely without typing your password or exposing it in your shell history:

```bash
echo $DOCKER_ACCESS_TOKEN | docker login -u $YOUR_DOCKER_USERNAME --password-stdin

# You will be prompted to enter your Docker Hub username and password
# Success message: You should see Login Succeeded in your terminal
```

### Step-8.4: Push Image to Docker Registry

```bash
# Tag your Image/Repository as per registry naming convention
docker tag $CURRENT_IMG_NAME $DOCKER_HUB_USERNAME/$IMAGE_NAME:$TAG

# Example
docker tag my-flask-app:v1 kbindesh/my-flask-app:v1

# Push the image to Docker registry
docker image push kbindesh/my-flask-app:v1
```

## 09. Advanced Docker Image Concepts

### 9.1 How to optimze Docker Images?

To optimize Docker images, you must:
  1. Minimize Image layer count
  2. Reduce the base image size
  3. Prevent unnecessary files from being copied to the Image.
  
- Smaller images build faster, deploy quicker, and reduce security vulnerabilities.

#### 9.2.1 Multi-stage Builds

- Multi-stage builds separate the compile environment from the runtime environment. 
- You leave heavy build tools behind and only copy production assets into the final image.

#### 9.2.2 Choose Minimal Base Images

- Avoid using default full operating system images like `ubuntu` or `node:latest`. 
- Switch to minimal, secure alternatives.
