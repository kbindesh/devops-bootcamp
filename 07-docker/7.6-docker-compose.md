# Managing Containers with `Docker Compose`

## Install and Configure Docker Compose

- Official Documentation: https://docs.docker.com/compose/install/

### Prerequisites

- Docker Host machine

### Install Docker Compose (v2)

- If you already have Docker Engine and Docker CLI installed, you can install the Docker Compose plugin from the command line in following ways:
  1. Using Docker's repository (https://docs.docker.com/compose/install/linux/#install-using-the-repository)
  2. Downloading and installing manually (https://docs.docker.com/compose/install/linux/#install-the-plugin-manually)

- _To download and install Docker Compose manually_, connect to your Docker host machine and run the following commands:

```bash
# Download and Install the Compose CLI plugin
DOCKER_CONFIG=${DOCKER_CONFIG:-$HOME/.docker}

# Create a new directory for compose
mkdir -p $DOCKER_CONFIG/cli-plugins

# Download the compose binary on the above location
curl -SL https://github.com/docker/compose/releases/download/v5.1.2/docker-compose-linux-x86_64 -o $DOCKER_CONFIG/cli-plugins/docker-compose

# Apply executable permissions to the binary
sudo chmod +x $DOCKER_CONFIG/cli-plugins/docker-compose

# To verify, check Docker Compose (v2) version
docker compose version
```

### Install and Configure Docker Buildx

- Official Documentation: https://github.com/docker/buildx/releases

```bash
mkdir -p ~/.docker/cli-plugins

# Download Buildx binary
curl -Lo ~/.docker/cli-plugins/docker-buildx https://github.com/docker/buildx/releases/download/v0.18.0/buildx-v0.18.0.linux-amd64

# Assign execute permission
chmod +x ~/.docker/cli-plugins/docker-buildx

# Check the buildx version
docker buildx version
```

## 01. Docker Compose - Overview

- **Docker Compose** is a Docker tool managing multi-container Docker applications.
- It is defined using the compose file (docker-compose.yaml) format.

- With a compose file, you can create and start all of the services defined in your configuration with a single command.

## 02. Understanding `declarative` vs `imperative` orchestration of containers

- Docker Compose is a Docker tool that is primarily used when you need to run and orchestrate containers running on a single Docker host.

- Docker Compose is embedded in the normal Docker CLI.
- Docker Compose uses files formatted in **YAML** format.
- By default, Docker Compose expects these files to be called **docker-compose.yml**, however other names are possible.
- The content of a **docker-compose.yml** file is a declarative way of describing and running a containerized **application essentially consisting of more than single container**.

- **What do you mean by `Imperative` here**?
  - This is a way in which we can solve problems by specifying the exact procedure that has to be followed by the system.

- **What do you mean by `Declarative` here**?
  - This is a way in which we can solve problems without requiring the developer to specify an exact procedure to be followed in order to accomplish a task.

  - You simply tell docker engine about your desired state for an application, and docker will figure out how to achieve it.
  - However this approach is inefficient and practically not possible to mid or large application with 100s of containers.
  - With the _Docker Compose_ tool, we are given a way to define the application in a declarative way in a file that uses the YAML format.

## 03. How Docker Compose works?

- Docker Compose relies on a YAML configuration file, usually named `compose.yaml` or `docker-compose.yml`.

- The **compose.yaml** file follows the rules provided by the Compose Specification in how to define multi-container applications.

### The Compose Application Model - `docker-compose.yaml`

The _⁠Docker Compose Application Model_ is a standardized framework for defining, launching, and managing multi-container applications using a single YAML configuration file.

The core framework relies on four primary high-level pillars/blocks defined by the _Compose_ Specification:

- **Services**
  - Computing components of an application are defined as _services_.
  - A _service_ is an abstract concept implemented on platforms by running the same container image, and configuration, one or more times.
    - **Image/Build**: Points to an official registry image or a local Dockerfile.

    - **Ports**: Maps host machine ports to internal container ports.
    - **Environment**: Injects key-value variables directly into the application runtime.

- **Networks**
  - Services communicate with each other through networks.
  - A network is a platform capability abstraction to establish an IP route between containers within services connected together.
    - **Service Discovery**: Allows containers to talk to each other using their service name instead of shifting IP addresses.
    - **Isolation**: Blocks external traffic from accessing sensitive internal containers (like database engines).
- **Volumes**
  - Volumes mount persistent data paths from your host machine into a container.
    - Persistence: Preserves stateful information (like database logs or user uploads) even if the container is wiped or rebuilt.
    - Sharing: Allows multiple distinct services to read or write to a synchronized shared space.
- **Configs**
  - You may have services that require configuration data that is dependent on the runtime or platform.
    - **Read-Only Mounting**: Docker mounts configs as standard read-only files at a customizable path inside the container.
    - **No Rebuilds Required**: You can update an external configuration file and restart the container to apply changes, avoiding the need to rebuild the entire Docker image.

- **Secrets**
  - Secrets can be for storing sensitive data that should not be exposed without security considerations.
  - Secrets are made available to services as files mounted into their containers.
    - **Secure Mounts**: Docker mounts secrets as temporary in-memory files inside the container (typically at `/run/secrets/<secret_name>`).
    - **No Disk Footprint**: Because they live in-memory (tmpfs), secrets are never accidentally committed to image layers or written to the container's writable disk layer.

### Sample docker-compose.yaml file

```yaml
name: secure-app-stack

services:
  web-server:
    image: nginx:latest
    ports:
      - "80:80"
    # 2. Grant the service access to specific configs and secrets
    configs:
      - source: nginx_rules
        target: /etc/nginx/nginx.conf
    secrets:
      - source: ssl_certificate
        target: /etc/nginx/certs/site.crt

  backend-api:
    image: my-api:v1
    environment:
      # Instruct your app code to read the password from the secret file path
      DB_PASSWORD_FILE: /run/secrets/db_root_pass
    secrets:
      - db_root_pass

# 1. Define the source files at the root level of the Compose model
configs:
  nginx_rules:
    file: ./config/nginx.conf

secrets:
  ssl_certificate:
    file: ./certs/live_site.crt
  db_root_pass:
    file: ./secrets/db_password.txt
```

### _Secrets_ vs _Configs_

| Feature              | `secrets` Block                     | `configs` Block                          |
| -------------------- | ----------------------------------- | ---------------------------------------- |
| **Primary Use Case** | Passwords, API tokens, Private keys | Nginx configs, .env files, JSON profiles |
| **Default Location** | /run/secrets/<name>                 | Container root or explicit target path   |
| **Storage Type**     | In-memory (tmpfs), secure           | Standard read-only file mount            |
| **Security Layer**   | Hidden from docker inspect logs     | Visible via inspection commands          |

## 04. Lab: Deploy multi-service Application with Docker Compose

### Step-4.1: Prerequisites

- **Docker Host** machine

### Step-4.2: Create a `docker-compose.yml` file

- Create a new directory on your Docker Host machine and label it as `example-compose-app`:

```bash
# Create a new directory for our App
mkdir example-compose-app

cd example-compose-app
```

- Now, create a new file `docker-compose.yml` and add below configuration to it:

```yaml
name: example-compose-app
services:
  db:
    image: postgres:alpine
    environment:
      - POSTGRES_USER=dockeruser
      - POSTGRES_PASSWORD=dockerpass
      - POSTGRES_DB=pets
    volumes:
      - pg-data:/var/lib/postgresql/data
      - ./db:/docker-entrypoint-initdb.d

  pgadmin:
    image: dpage/pgadmin4
    ports:
      - "5050:80"
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@acme.com
      PGADMIN_DEFAULT_PASSWORD: admin
    volumes:
      - pgadmin-data:/var/lib/pgadmin

volumes:
  pg-data:
  pgadmin-data:
```

- The above compose file has the following resources to deploy:
  1. postgresql (database) service

  2. pgadmin (sql client) service
  3. data volume for postgres service
  4. data volume for pgadmin service

- Now, create a folder called `example-compose-app\db` &rarr; create a file with label `init-db.sql` inside the _db_ directory.
  - This sql script will create a new table in the images database and insert few sample records to it.
  - You may refer to the sample [init-db.sql](./configs/init-db.sql) file for it's contents.

### Step-4.3: Deploy the Application with Compose

```bash
# Deploy an application in foreground
docker compose up

# (optional) Deploy an application in the background
docker compose up --detach
OR
docker compose up -d

# (optional) Deploying an app with compose file having a different name (other than docker-compose.yml)
docker compose  -f <docker_compose_file_name.yml> up
```

### Step-4.4: List all the Deployed Application Services

```bash
# List all the services associated with the App
docker compose ps

# List all the images
docker image ls
or
docker images

# List all the running Containers
docker container ls
or
docker ps

# List all the Volumes
docker volume ls
```

### Step-4.5: Access the deployed Application over the web

- As mentioned in the _docker-compose.yml_ file, **pgadmin (sql client) service** listens on **port 5050**, kindly allow ingress traffic on port `5050` on _Docker Host_ (EC2) security group.

- Open a browser &rarr; navigate to the following URI:

```bash
http://<PUBLIC-IP-OF-DOCKER-HOST>:5050.

# It should take you to the pgadmin login page.
```

- Login to pgadmin web UI using the credentials provided in the `docker-compose.yml` file.

### Step-4.6: Scale a service with Compose (manual)

```bash
# Syntax
docker compose up --scale <service_name>=<replicas>

# Example
docker compose up --scale web=3
```

### Step-4.7: Stop and Delete Application resources using Compose

```bash
# To stop and clean up the application resources
docker compose down

# Clean-up all the app resources along with volume
docker compose down -v

# Preceding command will delete all the containers, volumes and all the other resources associated with the App
```

## 05. Lab: `Building Images` with Compose

- The previous multi-service application had two pre-built images to deploy and didn't have any docker image to build.

- In this section, we will learn how you can:
  1. Package multiple services into respective docker images

  2. Deploy multi-service app using docker compose

- **Download/clone sample `Voting application` source code**
  - This simple **distributed voting application** runs across multiple Docker containers.

  - You may download or clone the code from this GitHub repo link: https://github.com/dockersamples/example-voting-app/tree/main
  - Once download, extract and open the folder in an IDE (VS Code)

### Step-5.1: Build Images and Push it to Registry using Compose

```bash
# Build the application
docker compose -f docker-compose.yml build

# To push all images to Docker Hub, we can use "docker compose push"
docker login -u <registry_username> -p <registry_password>

# Assuming the login succeeds, you can then push the image
docker compose -f docker-compose.yml push
```

### Step-5.2: Deploy Voting Application with Compose

```bash
docker compose up -d
```
