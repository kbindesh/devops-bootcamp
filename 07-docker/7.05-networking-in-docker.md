# Docker Networking

## 01. Overview

Docker networking allows containers to communicate with each other, the host machine, and external networks.

## 02. Core Concepts

Docker uses a Container Network Model (CNM) to manage container communication.

- **Sandbox**
  - Isolates the container network stack (router, interfaces, DNS).
- **Endpoint**
  - Connects a sandbox to a network (like a virtual network card).
- **Network**
  - A collection of interconnected endpoints.

## 03. Docker Network Drivers

Docker uses drivers to define how traffic flows. You choose the driver based on your architecture.

| Network Driver | Description                                                                                                                                                              | Scope       | Best Use Cases                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------- | ------------------------------------------------------------------------------------------------------- |
| **Bridge**     | The default network for standalone containers. Uses a virtual bridge to allow containers on the same host to communicate while isolating them from the external network. | Single-Host | Local development, testing, and apps running on a single machine.                                       |
| **Host**       | Removes network isolation between the container and the Docker host. Containers share the host's networking namespace directly.                                          | Single-Host | Maximizing network performance and applications that require low latency.                               |
| **Overlay**    | Creates a distributed virtual network across multiple Docker daemon hosts. Uses VXLAN to securely connect containers running on different physical or virtual machines.  | Multi-Host  | Swarm mode services, Kubernetes, and distributed microservices spanning a cluster.                      |
| **Macvlan**    | Assigns a physical MAC address to each container's virtual network interface. Makes the container appear as a physical device directly connected to your network.        | Single-Host | Migrating legacy VM setups, network monitoring, and applications requiring direct router/switch access. |
| **IPvlan**     | Similar to Macvlan, but does not assign unique MAC addresses to the containers. Solves switch port security and MAC address exhaustion limits.                           | Single-Host | Environments where you need physical network integration but face restrictions on MAC addresses.        |
| **None**       | Completely disables all networking for the container. Provides a completely isolated environment without loopback or external access.                                    | Single-Host | Highly secure batch processing, cryptography operations, or air-gapped workloads.                       |

### Port Mapping vs. Container Communication

By default, containers on different networks cannot talk to each other, and external traffic cannot reach inside a container.

- **Internal (Container-to-Container)**
  - Containers on the same user-defined bridge network communicate automatically using the container name as the domain name (Built-in DNS resolution).

- **External (Host-to-Container)**
  - You must expose ports using the -p or --publish flag to let outside traffic in.

## 04. `Lab`: Create a _Bridge_ Network and Deploy an Application into it

This lab will walk you through creating a user-defined _bridge network_ and deploying a multi-container application that communicates securely inside it:

- Node.js (backend)
- Redis (database)

### Step-4.1: Create the User-Defined Bridge Network

- First, create a custom bridge network.
- User-defined bridges provide automatic DNS resolution, allowing containers to talk to each other using their container names instead of unstable IP addresses.

```bash
docker network create my-app-net
```

### Step-4.2: Deploy the Database Container

- Deploy a **Redis** container inside the newly created network.
- By naming the container `redis-db`, other containers in the same network can reach it using `redis-db` as the hostname.

```bash
# Create a Container using redis:alpine image
docker run -d \
  --name redis-db \
  --network my-app-net \
  redis:alpine
```

### Step-4.3: Deploy the Backend Application Container

- Deploy a Node.js web application container into the exact same network.
  - We use `--network my-app-net` so it can see the Redis container.
  - We pass an environment variable `REDIS_HOST=redis-db` so the app knows where to connect.
  - We use `-p 3000:3000` to expose the app to our docker host machine.

```bash
# Create a Container using node:alpine image
docker run -d \
  --name web-app \
  --network my-app-net \
  -e REDIS_HOST=redis-db \
  -p 3000:3000 \
  node:alpine
```

### Step-4.4: Verify the Network Deployment

You can verify that both containers are successfully attached and communicating inside the network structure by inspecting it:

```bash
docker network inspect my-app-net

# Observe "Containers" section
```

- Look inside the **Containers** section of the JSON output. You will see both `redis-db` and `web-app` listed with their internal network IP addresses.

## 05. `Lab`: Deploy an Application into _Host_ Network

To deploy a Docker application into the Host network, you must use the `--network host` flag when starting your container.

### Step-5.1: Clean Up Port Conflicts

Ensure no existing services are using the port your container needs (Port 80 for Nginx).

```bash
# If this command returns any active processes, you must stop those services before proceeding
sudo lsof -i :80
```

### Step-5.2: Deploy the Container

```bash
# Pull the official Nginx image from registry
docker image pull nginx
OR
docker pull nginx

# Run the container using the --network host flag
# Do not use the -p or --publish flag, as port mapping is completely ignored in host networking mode

sudo docker container run --name app-in-host-nw --network host -d nginx
```

### Step-5.3: Verify the Network Configuration

Inspect the running container to verify that it has attached successfully to the host network.

```bash
sudo docker inspect app-in-host-nw --format '{{.HostConfig.NetworkMode}}'

# Expected Output: host
```

You can also check your active listening ports on the host system to see that Nginx is bound directly to it:

```bash
sudo ss -tulpn | grep :80
```

### Step-5.4: Test the Deployment

- Open your web browser and navigate directly to your host machine's IP address or http://localhost.
- You will instantly see the default Nginx welcome page without configuring any internal Docker port routing.

## 06. `Lab`: Deploy an Application into _None_ Network

- To deploy a Docker application into the None network, you must use the `--network none` flag when starting your container.

- This mode provides the highest level of network isolation by completely disabling the container's network stack.

- The container will only have a local loopback (127.0.0.1) interface.
- It cannot talk to the host, cannot reach the internet, and cannot be accessed from the outside.
- This is ideal for secure, offline processing tasks like batch computing, running cryptographic operations, or parsing untrusted files.

### Step-6.1: Download the Application Image

```bash
# Pull the alpine image from registry for testing
sudo docker image pull alpine
```

### Step-6.2: Deploy the Container with No Network

- Run the container using the `--network none` flag.
- Because we want to interact with it, we will use `-it` to open an interactive terminal.

```bash
sudo docker container run --name my-isolated-app --network none -it alpine sh
```

### Step-6.3: Verify the Network Configuration

```bash
sudo docker inspect my-isolated-app --format '{{.HostConfig.NetworkMode}}'

# Expected Output: none
```

### Step-6.4: Verify the Isolated Network Stack (inside the container)

Now that you are inside the container's command prompt (/ #), run the following command to check the available network interfaces:

```bash
ifconfig
or
ip addr

# Expected Output: You will see only the lo (loopback) interface listed. There will be no "eth0" or default gateway interfaces.
```

### Step-6.5: Test Outbound and Inbound Isolation (inside the container)

```bash
# Attempt to ping an external server like YouTube or Google's public DNS
ping -c 3 8.8.8.8

# Expected Output: ping: bad address '8.8.8.8' or Network is unreachable
```

Type _exit_ to close the container and return to your host machine's terminal.
