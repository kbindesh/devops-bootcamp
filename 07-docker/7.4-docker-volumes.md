# Managing Storage in Docker using `Volumes`

## Docker Storage - Overview

- Docker manages storage using three primary mount types (Volumes, Bind Mounts, and Tmpfs Mounts) along with built-in commands to clean up accumulated disk bloat.
- By default, data created inside a container is saved in a temporary writable layer and is lost when the container is deleted.

- To persist or manage data effectively, you must utilize Docker's storage mechanisms.

## Docker Storage - Key Concepts

- Ephemeral vs Persistent storage

- Storage Drivers
- Docker Volumes

## Core Docker Storage Mechanisms

The choice of storage mechanism depends directly on whether you need isolation, host filesystem access, or pure speed.

- **Volumes**
  - Best for persisting application data like databases.
  - Fully managed by Docker and stored in isolated host directories (/var/lib/docker/volumes/).

- **Bind Mounts**
  - Best for development environments.
  - They map any explicit file or directory from the host machine straight into the container.
- **Tmpfs Mounts**
  - Best for high-performance temporary data or sensitive keys.
  - Data is written strictly to the host's system memory and never hits the physical disk.

## 01. Lab: Creating and Mounting Data volumes

### Modifying the Container layer and check the difference

```bash
# Run a container and Create a new file inside it
docker container run --name demo alpine /bin/sh -c 'echo "test message" > test.txt'

# Use the diff command to find out what has changed in the container's filesystem as compared to original image
docker container diff <container_name>

docker container diff demo
```

- Now, if the container is deleted from memory, its container layer will also be removed, and with it, all the changes will be irreversibly deleted.

- If we need our changes to persist even beyond the lifetime of the container, **Docker volumes** are the solution.

### Create a Volume | List | Inspect

```bash
docker volume create <volume_name>

docker volume create datavolume
```

- The default volume driver is the so-called **local driver**, which stores the data locally in the host filesystem.

- **List all the Volumes known to Docker**

```
docker volume ls

# Reference
https://docs.docker.com/reference/cli/docker/volume/ls/
```

- **Get more details about a particular Docker Volume**

```
docker volume inspect <volume_name>

docker volume inspect datavolume
```

### Mounting a volume on Container

- Once we have created a named volume, we can mount it into a container by following these steps:

```bash
# Use the --volume or -v parameter with docker container run command
docker container run -it --name <container_name> -v <vol_name>:/<dir> alpine /bin/sh

docker container run -it --name container2 -v datavolume:/data alpine /bin/sh

# Inside the container, we can now create files in the /data folder
/ # cd /data
/ # echo "Some app code" > Code-01.txt
/ # echo "Some more code" > Code-02.txt

# Exit from the Container
Press Ctrl+D
```

### Delete the Container with Volume mounted on it

```bash
# Delete the container we created in the previous step
docker container rm container2
```

### Create a new Container and mount the Volume created in prev step

```bash
docker container run --name container4 -it --rm \
-v datavolume:/app/data \
centos:7 /bin/bash
```

- Once you're inside the CentOS container, we can navigate to the `/app/data` folder to which we have mounted the volume and list its content:

```bash
cd /app/data
ls –l

# As expected, we should see the two files create in step#2
Code-01.txt
Code-02.txt

# Exit from the Container
Press Ctrl+D
```

### Removing Volumes

```bash
# To remove/delete one volume
docker volume rm <volume_name>

# To check the list of all the remaining Data volumes
docker volume ls

# To remove all the containers to clean up
docker container rm -v -f $(docker container ls -aq)
```

## 02. Lab: `Sharing Data` between containers `using Docker Volumes`

- Containers are like sandboxes for the applications running inside them.

- This is really helpful to protect applications running in different containers from conflicting with each other.
- It means that the whole filesystem visible to an application running inside a container is private to that application, and no other application running in a different container can interfere with it.
- **Sample Use-case**:
  - We want to share data between containers.

  - Say an application running in **container-A** produces some data that will be consumed by another application running in **container-B**.
  - In order to make it work, we can create a volume and mount it to _container-A_, as well as to _container-B_.

```bash
# Create a container and mount a volume on it | Default volume mode: R/W
docker container run -it --name ContainerWithRWVolume -v shared-data:/data .alpine /bin/sh

# Create a new file inside the container (on mounted volume)
/ echo "New file present in docker volume" > /data/test-file.txt

# Now, exit from the container by pressing Ctrl+D or exit

# Create another container, say ContainerWithROVolume and mount a volume in Read Only mode
docker container run -it --name ContainerWithROVolume -v shared-data:/app/data:ro ubuntu:22.04 /bin/bash

# Check in the container if you can see the file created in the ContainerWithRWVolume container
ls -l /app/data

# Now, try to create a new file on the mounted volume
/ echo "New file for read only volume" > /app/data/test-file-2.txt

# It will fail with the following message:
bash: /app/data/test-file-2.txt: Read-only file system
```

- Exit from the container and remove all the containers and volumes once done with the lab.

```bash
docker container rm -f $(docker container ls -aq)

docker volume rm $(docker volume ls -q)
```

## Bind Mount

- A _Docker bind mount_ links a specific, absolute file or directory on your host machine directly into a container.

- Unlike volumes, which Docker creates and manages securely in its own directories, a _bind mount_ relies entirely on your host's existing filesystem structure and can reference any path on your drive.
- If you edit a file on your host machine, the changes instantly appear inside the container.
- If the container modifies the file, the changes instantly appear on your host.

### When to Use Bind Mounts?

- **Source Code Sharing**: Passing source code or build artifacts into a container for active development.

- **Config File Sharing**: Injecting a specific host configuration file (e.g., mounting a specific /etc/nginx/nginx.conf file) into a container.
- **Log Collection**: Mapping a container's log directory to a host folder so external monitoring tools can parse them easily.

### Lab: Deploy App Container with Bind Mount Storage

#### Setup Your Host Directory

- On your host computer, create a project folder and add an index.html file:

```bash
mkdir ~/my-project

cd ~/my-project

echo "<h1>Hello from the Host Machine!</h1>" > index.html
```

#### Run the Container with a Bind Mount

- Create a new Container and Mount your local folder into the Nginx container's default web server directory (`/usr/share/nginx/html`) using the **-v** flag (format: `-v /host/absolute/path:/container/path`):

```bash
docker run -d -p 8080:80 -v ~/my-project:/usr/share/nginx/html --name web-dev nginx

OR

# More explicit --mount flag (recommended for clarity)
docker run -d -p 8080:80 --mount type=bind,source=$HOME/my-project,target=/usr/share/nginx/html --name web-dev nginx
```

#### Test and Edit Live

- Open your browser and navigate to http://docker-host-public-ip:8080.
- You will see "Hello from the Host Machine!".
- Open the `index.html` file on your actual computer using any text editor.
- Change the text to "Live updates work!" and save the file &rarr; Refresh your browser.
- The container reflects the change immediately without a restart.
