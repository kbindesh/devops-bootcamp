## What are `Docker Images`?

- A **Docker image** is a read-only template that contains a set of instructions for creating a container that can run on the Docker platform.

- It provides a convenient way to package up applications and preconfigured server environments, which you can use for your own private use or share publicly with other Docker users
- A Docker image is made up of a collection of files that bundle together all the essentials, such as:
  - Installations
  - Application code
  - Dependencies – required to configure a fully operational container environment.

### The `Layered Filesystem` of Docker Image

- Container images are templates from which containers are created.
- These images are not made up of just one monolithic block but are composed of many layers.
- The first layer in the image is also called the **base layer**.
- Each layer contains some files and folders.
- Each layer only contains the changes to the filesystem concerning the underlying layers.
- The **layers of a container image are all immutable**. Hence, once generated, the layer cannot ever be changed.

## What is `Docker Build Context`?

- The `Docker Build Context` is the set of local files and directories that the Docker engine can access during the image building process.
- When you run `docker build .` command , the "." specifies that your current working directory is the build context.

1.  Local Context
2.  Remote Context

### How Docker Build Context Works?

- Any files you want to include in your image using `COPY` or `ADD` instructions in your _Dockerfile_ must exist within this context.

- **Path or URL**
  - You can provide a local directory path, a Git repository URL, or even a remote tarball as the context.

- Traditionally, the entire context is packaged and sent to the Docker daemon (the engine doing the building).
- Newer Docker BuildKit optimizations allow the engine to request only the specific files it needs as it reaches each step.
- : For security and predictability, a Dockerfile cannot access files outside of its build context (e.g., you cannot COPY ../secret.txt /).

- **Multiple Contexts**
  - Modern Docker versions allow you to define multiple named contexts, letting you pull files from different locations into a single build.

## `Dockerfile`

- A Dockerfile is a plain text file containing a sequential list of instructions used to automatically build a Docker image.

- Here is a comprehensive breakdown of the most common Dockerfile instructions, ordered by how they typically appear in a file:

### Initialization and Setup

- **FROM**
  - Sets the base image for the subsequent instructions.
  - Every valid _Dockerfile_ must start with this instruction.
  - Example: `FROM python:3.11-slim`

- **ARG**
  - Defines variables that users can pass at build-time using `docker build --build-arg <varname>=<value>`.
  - It is the only instruction that can precede `FROM` instruction.
  - Example: `ARG VERSION=latest`

- **WORKDIR**
  - Sets the working directory for any subsequent RUN, CMD, ENTRYPOINT, COPY, and ADD instructions.
  - It creates the directory if it does not exist.
  - Example: WORKDIR /usr/src/app
