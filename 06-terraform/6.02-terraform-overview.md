# Hashicorp Terraform Overview

## Terraform Overview

- `Terraform` is an open-source, IaC tool created by _HashiCorp_.
- It allows you to safely and predictably create, change, and improve infrastructure by using declarative configuration files instead of manual mouse-clicks or custom scripts.

## Terraform Core Concepts

- To understand Terraform, you need to understand its four foundational components, as follows:
  1. **HashiCorp Configuration Language (HCL)**
     - The human-readable, declarative language used to write Terraform files (ending with .tf).
     - You describe what you want, and Terraform figures out how to build it.
  2. **Providers**
     - Plugins that act as translators between Terraform and external APIs. Providers exist for major cloud vendors (AWS, Azure, GCP), SaaS platforms, and on-premises hardware.
  3. **State File**
     - A private JSON document (terraform.tfstate) that acts as Terraform's source of truth. It maps your code configuration to the real-world resources deployed in your cloud account.
  4. **Modules**
     - Self-contained packages of Terraform configurations that allow you to group related resources together, creating reusable infrastructure blueprints.

## Terraform Workflow - 5-Step Lifecycle

- The Terraform workflow is the core operational lifecycle used to write, preview, and deploy infrastructure safely.

```bash
[ WRITE ] ──> [ INIT ] ──> [ VALIDATE ] ──> [ PLAN ] ──> [ APPLY ]
```

### 1. `WRITE` the Terraform script

- You write your infrastructure definitions in files ending with a `.tf` extension.
- Language: HCL
- Example: You write a block of code stating you want to create an AWS EC2 Instance.

### 2. `INITialize` the directory

- Before Terraform can do any work, you must prepare your local directory.
- Running `terraform init` command scans your configuration files to see which cloud provider (vendor) you are using and download the required Provider Plugins (like the AWS, Azure) and stores them in a hidden local directory.
- It also sets up your backend storage for tracking infrastructure.

### 3. `VALIDATE` the Terraform script

- Running `terraform validate` checks whether your Terraform configuration files are syntactically valid and internally consistent.
- It acts as a local linter, scanning your code for errors before Terraform attempts to access your remote cloud provider.

### 4. Check the Terraform `PLAN`

- This is a "dry run" safety step that allows you to preview modifications before touching live environments.
- Running `terraform plan` queries your cloud provider to see what is currently running, compares it against your local code, and looks at your terraform _state file_.
- It generates a delta report showing exactly what will happen if you proceed:
  - \+ Create
    - New resources that will be built.
  - \~ Update
    - Existing resources modifying their parameters in place.
  - \- Destroy
    - Existing resources that will be deleted.

### 5. `APPLY` the Terraform script

- When you run `terraform apply`, Terraform recalculates the plan and prompts you for a manual yes confirmation.
- Once confirmed, it makes real-world API calls to your cloud vendors (e.g. AWS,Azure) to build, change, or delete resources in the exact order required.
- After successful provisioning, it saves the final configuration mapping into your `terraform.tfstate` file.
