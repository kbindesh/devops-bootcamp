### Helm - Core Built-in Objects

- In Helm, Built-in Objects are top-level data structures passed into the template engine automatically.
- They allow you to dynamically inject metadata about the deployment, configuration values, cluster traits, and files directly into your Kubernetes manifest templates.

- All built-in objects in _Helm_ begin with a capital letter and are accessed from the root context, which is represented by a dot (.)

| Object            | Description                                                                          | Key Fields / Functions                                                                           |
| ----------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **.Release**      | Information about the current deployment instance.                                   | [.Release.Name, .Release.Namespace, .Release.IsInstall, .Release.Revision](http://release.name/) |
| **.Values**       | Configuration attributes passed into the chart via values.yaml or CLI flags.         | Any user-defined keys (e.g., .Values.image.tag)                                                  |
| **.Chart**        | Metadata contents defined inside the chart's Chart.yaml file.                        | [.Chart.Name, .Chart.Version, .Chart.AppVersion](http://chart.name/)                             |
| **.Files**        | Provides access to read non-special, external files inside the Helm chart.           | .Files.Get, .Files.GetBytes, .Files.Glob                                                         |
| **.Capabilities** | Details about what features and API versions the target Kubernetes cluster supports. | .Capabilities.APIVersions.Has, .Capabilities.KubeVersion                                         |
| **.Template**     | Information about the current template file being executed.                          | .Template.Name, .Template.BasePath                                                               |

#### .Release Object

This object describes the specific deployment execution (the "release"). It tracks state parameters like whether this is a fresh installation or an upgrade.

- _.Release.Name_
  - The unique name assigned to the release instance.
- _.Release.Namespace_
  - The target Kubernetes namespace for the release.
- _.Release.IsUpgrade_
  - Evaluates to true if the operation is a helm upgrade or helm rollback.

```yaml
# Naming a Kubernetes resource dynamically using the release name to prevent naming collisions

apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
  namespace: {{ .Release.Namespace }}
data:
  is_fallback: "{{ .Release.IsUpgrade }}"
```

#### .Values Object

This object exposes the variables defined inside your values.yaml file. It allows operators to customize chart behavior without altering structural manifest code.

- Example: Suppose your values.yaml contains:

```yaml
replicaCount: 3
image:
  repository: nginx
  tag: "1.25"
```

You read those parameters inside a deployment.yaml template like this:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: { { .Values.replicaCount } }
  template:
    spec:
      containers:
        - name: nginx
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

#### .Chart Object

This object lets you access data from the structural `Chart.yaml` file. It is perfect for injecting hardcoded structural tracking, labels, and chart versioning automatically.

- _.Chart.Name_
  - The name of the chart.
- _.Chart.Version_
  - The semantic version of the Helm chart package.

```yaml
# Applying standard metadata labels to a resource

apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-service
  labels:
    helm.sh/chart: "{{ .Chart.Name }}-{{ .Chart.Version }}"
    app.kubernetes.io/name: {{ .Chart.Name }}
```

#### .Files Object

Instead of copying plain text configuration directly into templates, the .Files object allows you to read files bundled inside your chart directory (excluding the templates/ directory).

- _.Files.Get_
  - Fetches the contents of a file as a string.
- _.Files.AsConfig_
  - Emits file bodies as a valid structural YAML map.

Example &rarr; Loading a configuration file (app-config.ini) directly into a Kubernetes ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-application-ini
data:
  app-config.ini: |-
{{ .Files.Get "app-config.ini" | indent 4 }}
```

#### .Capabilities Object

This allows you to query the target Kubernetes cluster directly. You can alter template generation conditionally depending on the features or APIs the cluster possesses.

- Example:
  - Checking if the cluster supports _networking.k8s.io/v1_ before utilizing it for an Ingress manifest:

```yaml
{{- if .Capabilities.APIVersions.Has "networking.k8s.io/v1" }}
apiVersion: networking.k8s.io/v1
{{- else }}
apiVersion: networking.k8s.io/v1beta1
{{- end }}
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
```

## 04. Hands-on Lab: Installing Your First Helm Chart

In this section, we will install Nginx (a web server) from a public repository onto our Kubernetes cluster.

### Step-01: Add the Repository

First, you need to tell Helm where the "app store" for Bitnami charts is located.

```bash
helm repo add bitnami https://bitnami.com
```

### Step-02: Update Your Local Cache

Ensure your Helm client has the absolute latest list of charts available from that repository.

```bash
helm repo update
```

### Step-03: Install the Chart

Now, run the _install_ command. We will name our specific deployment instance `my-web-server` and point it to the _bitnami/nginx_ chart.

```bash
helm install my-web-server bitnami/nginx
```

- What happens behind the scenes:
  1. Helm downloads the Nginx chart from the repository.
  2. It reads the default settings from the chart's values.yaml.
  3. It generates the Kubernetes manifests and sends them to your cluster.
  4. It creates Revision 1 of your release named my-web-server.

### Step-04: Verify the Installation

You can view your active Helm deployments by running:

```bash
helm list

# You will see my-web-server listed with a REVISION number of 1
```
