# Working with Pods

## 01. What is Pod?

- The smallest deployable unit of application in Kubernetes is a **pod**.
- A Pod contains the actual application workload.
- A Pod can have one or more containers associated with it.
- A **Pod** in Kubernetes has a defined lifecycle.

## 02. Pod Operations

### 2.1 Explain Pod attributes

- The following command shows a complete list of Pod attributes:

```bash
$ kubectl explain pods --recursive

# To get the details about a particular Pod attribute
kubectl explain pod.spec.restartPolicy
```

### 2.2 Deploying Pods

#### Create a Pod - `imperative` approach

```bash
# Syntax to create a Pod
kubectl run <pod-name> --image=<image-name:image-tag>

# Example-01: Create a Pod with nginx:alpine image
kubectl run --image=nginx:alpine bin-nginx-pod

# Example-02: Create a Pod with busybox image
kubectl run busybox --rm -it --image=busybox /bin/sh
```

#### Create a Pod - `declarative` approach

- Create a YAML file with the Pod specification as follows:

```
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:alpine
    ports:
    - containerPort: 80
```

- Deploy above yaml K8s manifest:

```
# Deploy a k8s manifest
kubectl apply -f <MANIFEST_NAME>.yaml
```

### Viewing and Inspecting Pods

```
# List all the pods present in default namespace
kubectl get pods

# List all the pods alongside internal IP addresses and host Node labels
kubectl get pods -o wide

# List all the pods from all the namespaces
kubectl get pods -A

# Fetch pod's low-level diagnostic logs, structural configuration properties, and lifecycle event records
kubectl describe pod $POD_NAME
```

### Debugging and Logging

```bash
# Fetch standard Pod logs
kubectl logs $POD_NAME

# Fetch logs from a multi-container Pod
kubectl logs $POD_NAME -c $CONTAINER_NAME

# Pod's Live Stream Tail | Observe real-time application behavior and errors
kubectl logs -f $POD_NAME
```

### Interacting with Running Pods

```bash
# Run any command inside a Pod's container through interactive shell execution
kubectl exec -it $POD_NAME -- /bin/bash

# Single command execution inside a Pod's container
kubectl exec -it $POD_NAME -- env

# Network Port Forwarding
kubectl port-forward nginx-pod 8080:80

# Move directories and assets seamlessly between your host machine and Pod
kubectl cp ./local-file.txt nginx-pod:/tmp/remote-file.txt
```

### Modifying/Updating Pods

```bash
# Update Pod schema live by editing it
kubectl edit pod $POD_NAME

# Add a Label to an existing Pod
kubectl label pods $POD_NAME env=production
```

### Deleting Pods

```bash
# Delete a Pod gracefully
kubectl delete pod $POD_NAME

# Delete a Pod forcefully
kubectl delete pod $POD_NAME --grace-period=0 --force

# Purge current namespace Pod workloads
kubectl delete pods --all
```

## 03. Requests and Limits

In Kubernetes, requests and limits are the mechanisms used to control and regulate the CPU and memory consumption of your containers.

- _Requests_
  - Requests represent the minimum guaranteed resources a container needs to run.
  - K8s uses this metric to find a proper _Node_ for scheduling the Pod.
- _Limits_
  - Limits represent the absolute maximum resources a container is allowed to consume.
  - This prevents a single container from dominating the Node's resources.

### Pod Requests and Limits - Key Differences

| Feature         | Requests                               | Limits                                             |
| --------------- | -------------------------------------- | -------------------------------------------------- |
| Primary Purpose | Pod Scheduling (Finding a Node)        | Runtime Enforcement (Resource capping)             |
| Guaranteed?     | Yes, fully reserved for the Pod.       | No, only available if the Node has spare capacity. |
| Can it go over? | Yes, if the Node has unallocated room. | No, hard ceiling enforced by the OS kernel         |

### Lab: Create a Pod with Resource Requests & Limits

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app-pod
spec:
  containers:
    - name: web-container
      image: nginx:latest
      resources:
        requests:
          memory: "256Mi" # 256 Mebibytes
          cpu: "500m" # 500 millicores (0.5 CPU core)
        limits:
          memory: "512Mi" # 512 Mebibytes
          cpu: "1000m" # 1000 millicores (1 full CPU core)
```

## 04. Understanding a Multi-container Pod

- Multi-container pods are simply pods with more than one container working together as a single unit.

- When it comes to multiple containers residing in a pod, a container interacts with another in the following two ways:
  - Shared networking
  - Shared storage volumes

### Create a Multi-container Pod

```
apiVersion: v1
kind: Pod
metadata:
  name: multi-app-pod
  labels:
    app: multi-app
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80
  - name: busybox-sidecar
    image: busybox
    command: ['sh', '-c', 'while true; do sleep 3600; done;']
```

### Real-World Scheduling Scenario

Imagine you have a Kubernetes Node with 2 CPU Cores and 2 GiB of RAM available:

- Scheduling Time
  - You deploy the web-app-pod from the YAML above.
  - The Kubernetes Scheduler checks the node's capacity against the Pod's Requests (`500m` CPU / `256Mi` RAM).
  - Since the node has plenty of room, the Pod is scheduled successfully.
- Idle State
  - The app is idling and uses only `50m` CPU and `100Mi` RAM.
  - This is perfectly normal; requests just reserve the capacity, they do not force the app to use it.
- Traffic Spike (Burstable Behavior)
  - A surge of users hits the application. The container scales up its resource usage beyond its initial request.
  - It attempts to draw `800m` CPU. Because the node has idle capacity and this is below the `1000m` Limit, K8s permits it.
  - It attempts to allocate `600Mi` RAM. Because this breaks the hard Limit of `512Mi`, the kernel instantly steps in and terminates the container process (OOMKilled) to safeguard the Node.

## 05. Liveness Probes

- A Liveness Probe is a diagnostic mechanism Kubernetes uses to check if a containerized application inside a pod is still alive and running properly.

- If an application deadlocks, freezes, or crashes internally, the container might stay "running" from Docker's perspective, but it stops serving traffic.
- When a liveness probe fails, Kubernetes automatically kills the unhealthy container and restarts it to restore service.

### How a Liveness Probe Works?

```
[ Pod Starts ]
      │
      ▼
( Wait for 'initialDelaySeconds' )
      │
      ▼
┌─► [ K8s executes the probe check ]
│     │
│     ├──► PASS: Do nothing. Wait for 'periodSeconds', then check again. ──┐
│     │                                                                   │
│     └──► FAIL: Increment failure count.                                 │
│            │                                                            │
│            ├──► Fails < 'failureThreshold': Wait, then retry. ──────────┤
│            │                                                            │
│            └──► Fails == 'failureThreshold': K8s restarts container! ───┘
```

- Step-1: _Pod Initialization_: The container starts up normally.

- Step-2: _Grace Period_: K8s waits for a user-defined startup delay (initialDelaySeconds) to allow the application to boot up before checking its health.

- Step-3: _Periodic Checks_: Kubernetes runs a specific health check command or network request against the container at a regular interval (periodSeconds).
- Step-4: _Evaluation_
  - _Success_: The application is healthy. K8s resets the failure counter and waits for the next interval.
  - _Failure_: The application did not respond correctly within the allowed time (timeoutSeconds).
- Step-5: _Remediation_: If the probe fails consecutively up to a set limit (failureThreshold), K8s marks the container as unhealthy, terminates it, and spins up a fresh instance.

### Types of Liveness Probes

Kubernetes offers four ways to check container health:

1. HTTP GET
   - Hits an HTTP endpoint (like /healthz)
   - Returns success if the status code is between 200 and 399.
2. TCP Socket
   - Tries to open a TCP connection to a specific port.
   - Succeeds if the port is open.
3. Exec Command
   - Runs a script or command inside the container.
   - Succeeds if the command exits with code 0.
4. gRPC
   - Performs a native gRPC health check call.

### Lab: Create a Pod with Liveness Probe

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: liveness-example-pod
spec:
  containers:
    - name: web-app
      image: nginx:latest
      ports:
        - containerPort: 80
      livenessProbe:
        httpGet:
          path: /healthz # The app endpoint to check
          port: 80 # The port the app listens on
        initialDelaySeconds: 15 # Wait 15s after startup before checking
        periodSeconds: 10 # Run the check every 10 seconds
        timeoutSeconds: 2 # Expect a response within 2 seconds
        failureThreshold: 3 # Restart container after 3 consecutive failures
```

### Real-World Failure Scenario - Liveness Probe

Imagine you deploy a Python web application that has a memory leak or a thread deadlock issue.

1. Normal State
   - The pod runs fine. Every 10 seconds, Kubernetes sends an HTTP request to `/healthz`.
   - The app responds with 200 OK.
2. The Freeze
   - A thread deadlocks inside the application.
   - The app process is still active, but it completely stops responding to requests.
3. First Failure
   - Kubernetes hits /healthz.
   - The application hangs and fails to respond within `timeoutSeconds: 2`.
   - Failure count = 1.
4. Threshold Reached
   - Ten seconds later, it fails again (count = 2).
   - Ten seconds later, it fails a third time (count = 3).
5. The Restart
   - Because the failureThreshold of 3 is reached, K8s instantly destroys the broken container and launches a new one, clearing the deadlock and restoring uptime automatically.

## 06. Readiness Probes

- A Readiness Probe is a diagnostic mechanism K8s uses to determine if a container is ready to accept network traffic from users or other services.

- While a Liveness Probe decides if a container needs a restart, a Readiness Probe decides if a container should receive traffic.
- If a readiness probe fails, K8s leaves the container running but removes the Pod from the Service load balancer, preventing users from hitting a broken or booting application.

### Why Readiness Probes are needed?

- When an application starts up, it often needs time to load configurations, warm up caches, or connect to a database.
- If Kubernetes sends user traffic to the Pod immediately, users will experience 502 Bad Gateway or connection timeout errors.
- The Readiness Probe acts as a safety gate.

```
                  ┌───► [ Pod Booting ]  ─────► Probe Fails ──► Traffic Blocked ❌
                  │
[ Traffic In ] ───┼───► [ Pod Warming Up ] ───► Probe Fails ──► Traffic Blocked ❌
                  │
                  └───► [ Pod Fully Ready ] ──► Probe Passes ─► Traffic Allowed  ✅
```

### Lab: Create a Pod with Readiness Probe (HTTP GET)

Here is a standard configuration using an HTTP endpoint (like /healthz/ready or /ready):

```bash
apiVersion: v1
kind: Pod
metadata:
  name: readiness-example-pod
  labels:
    app: web-service
spec:
  containers:
  - name: enterprise-app
    image: my-app:v1.0
    ports:
    - containerPort: 8080
    readinessProbe:
      httpGet:
        path: /ready              # Endpoint dedicated to checking dependencies
        port: 8080
      initialDelaySeconds: 10     # Give the app 10s to start up before checking
      periodSeconds: 5            # Check readiness every 5 seconds
      successThreshold: 1         # 1 successful check marks it as ready
      failureThreshold: 2         # 2 consecutive failures removes it from traffic
```

### Real-world Scenario - Readiness Probe

Imagine you are deploying a Java Spring Boot application that takes 30 seconds to fetch initial data from a database and warm up its internal cache.

1. Deployment Phase
   - You run `kubectl apply`.
   - The Pod transitions to the Running state, but the app code inside is still booting up.
2. Traffic Protection
   - Because of the readiness probe, the Pod's status is listed as 0/1 READY.
   - If a user goes to your website, K8s does not send their request to this new Pod.
3. Passing the Check
   - After 30 seconds, the app successfully connects to the database.
   - The next check to /ready returns a 200 OK status.
4. Traffic Injection
   - The Pod status changes to 1/1 READY. K8s instantly adds the Pod's IP address to the Service endpoints, and users can now smoothly access the app.

5. Runtime Failure (Database drops)
   - Mid-day, the backend database goes down.
   - The app's `/ready` endpoint begins returning a 500 Internal Server Error.
   - The probe fails twice. K8s immediately removes the Pod from the load balancer.
   - Users are spared from seeing errors, and their traffic is routed to other healthy Pods instead.

## 07. Node Selectors

- A nodeSelector is the simplest recommended way to constrain a K8s Pod to run only on specific nodes within a cluster.
- It uses exact-match key-value pairs (labels) to tell the K8s scheduler which nodes are eligible to host the Pod.

### How `nodeSelector` works?

1. Label the Node
   - You assign custom text labels (key-value pairs) to your cluster's worker nodes.
2. Assign the Selector
   - You add a nodeSelector field to your Pod's YAML configuration matching those exact labels.
3. Strict Scheduling
   - The Kubernetes scheduler searches for a node that matches all specified labels.
   - If no matching node is found, the Pod will remain in a Pending state.

### Lab: GPU Workload Placement Example

Imagine you have a Pod that processes heavy graphical data and absolutely requires a node equipped with an Nvidia GPU.

#### Step-01: Label your node

- First, find the name of your node and apply a custom label to it using the ⁠Kubectl command-line tool.

```
kubectl label nodes worker-node-01 hardware=gpu
```

#### Step-02: Configure your Pod YAML

In your Pod specification file, add the nodeSelector block under the spec section:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-processing-pod
spec:
  containers:
    - name: data-cruncher
      image: nginx
  # The nodeSelector forces placement on the labeled node
  nodeSelector:
    hardware: gpu
```

#### Step-03: Deploy the Pod

Deploy your file to the cluster:

```bash
kubectl apply -f pod.yaml
```

The scheduler will evaluate all available nodes, see that `worker-node-01` has the label `hardware=gpu`, and successfully place your gpu-processing-pod onto that node.

### nodeSelectors - Key Behavioral Rules

- AND Logic Only
  - If you define multiple labels inside `nodeSelector`, the target node must match all of them.
  - It operates using strict standard AND logic.

- Hard Requirement
  - It is a rigid constraint.
  - If the keys or values do not match exactly, the Pod will not deploy to that node - even if the cluster has plenty of idle CPU and memory.

- Built-in Labels
  - You do not always have to manually label nodes.
  - K8s automatically injects default labels you can target right away, such as `kubernetes.io/hostname` or `topology.kubernetes.io/zone`.

## 08. Affinity and Anti-affinity

### Kubernetes Node and Pod Affinity Rules

- K8s **Affinity** and **Anti-Affinity** expand on `nodeSelector` by allowing you to define flexible, advanced scheduling rules using complex logic, expressions, and soft preferences.

### Core Concepts

- Affinity
  - Attracts Pods to specific locations (nodes or other Pods).
- Anti-Affinity
  - Repels Pods away from specific locations to prevent resource crowding or ensure high availability.
- Node vs. Pod Scope
  - _Node Affinity_ targets node characteristics (labels on nodes).
  - _Pod Affinity/Anti-Affinity_ targets workloads (labels on existing, running Pods).

#### The Two Rule Types

1. **Hard Rule** (requiredDuringSchedulingIgnoredDuringExecution): The constraint must be met. If no matching nodes exist, the Pod stays Pending.

2. **Soft Rule** (preferredDuringSchedulingIgnoredDuringExecution): The scheduler tries to meet the rule. If it cannot, it schedules the Pod anyway on the next best node.

### Node Affinity (Advanced Node Matching)

- **Example Title**: Multi-Zone Database Deployment
- Imagine you want to place a production database Pod only in specific cloud zones, preferring high-performance storage if available:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: production-db
spec:
  affinity:
    nodeAffinity:
      # 1. HARD RULE: Must be in us-east-1a or us-east-1b
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                  - us-east-1a
                  - us-east-1b
      # 2. SOFT RULE: Prefer nodes with NVMe drives, but don't fail if unavailable
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          preference:
            matchExpressions:
              - key: storage-type
                operator: In
                values:
                  - nvme
  containers:
    - name: mysql
      image: mysql:8.0
```

### Pod Affinity (Co-locating Workloads)

- **Example Title**: Low-Latency Web and Cache Co-location

- Imagine a web application that talks constantly to a Redis cache. To minimize network latency, you want the Web Pod to land on the exact same physical node where the Redis Pod is already running.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
spec:
  affinity:
    podAffinity:
      # HARD RULE: Must land on a node already running a "app=redis" Pod
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - redis
          # topologyKey defines the boundary (e.g., same physical hostname)
          topologyKey: kubernetes.io/hostname
  containers:
    - name: web-server
      image: nginx
```

### Pod Anti-Affinity (Spreading Workloads)

- Example Title: High-Availability Web Replica Spreading

- Imagine you are running three replicas of a web server. If one worker node crashes, you do not want all replicas to go down. You use anti-affinity to ensure replicas never share the same node.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app-replica
  labels:
    app: web-server
spec:
  affinity:
    podAntiAffinity:
      # HARD RULE: Do NOT land on a node already running a "app=web-server" Pod
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - web-server
          topologyKey: kubernetes.io/hostname
  containers:
    - name: web-server
      image: nginx
```

## 09. FAQs

### What Happens When Pod Limits Are Exceeded?

The behavior depends strictly on the resource type because CPU is compressible, while memory is not.

- CPU Exceeded
  - The container is throttled. The kernel restricts its CPU cycles, causing the application to run slower, but it does not crash.
- Memory Exceeded
  - The container is terminated by the Linux kernel Out-Of-Memory (OOM) killer. Kubernetes will report the Pod status as OOMKilled and attempt a restart.
