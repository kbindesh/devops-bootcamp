# Identity and Access Management in Kubernetes

- K8s does not have a built-in user database.
- K8s relies on an external identity provider to authenticate users, while using internal mechanisms to authorize what those authenticated users can do.

- For DevOps engineers and Kubernetes administrators, mastering Kubernetes Identity and Access Management (IAM) is critical to securing clusters and enforcing the principle of least privilege.

- Kubernetes handles this process through a strict, multi-step pipeline executed in sequential order:

## 01. Authentication (AuthN): Who are you?

- Authentication is the first line of defense.
- Kubernetes categorizes cluster clients into two distinct groups:
  1. **Normal Users** (managed externally)
     - These are humans (devs, admins) or external services.
     - K8s does not store "User" objects in its database (etcd).
     - K8s validates users via external mechanisms like OIDC (OpenID Connect) (e.g., Okta, Google Workspace, Azure AD), X.509 Client Certificates, or Static Token Files.

  2. **ServiceAccounts** (managed by Kubernetes)
     - These are identities meant for processes/pods running inside the cluster.
     - They are native K8s resources managed via the API.
     - When you create a ServiceAccount, Kubernetes automatically generates a token (via the TokenRequest API) and mounts it into the pod so the application can authenticate with the API server.

### Core Authentication Methods

Kubernetes supports several plugins to parse credentials:

- **X.509 Client Certificates**
  - The API server verifies the client's certificate against a trusted Cluster Certificate Authority (CA).
  - The certificate's Common Name (CN) maps to the username, and the Organization (O) fields map to groups.
  - This is commonly used for cluster components (like kubelet to API server communication) and initial admin configuration.

- **OpenID Connect (OIDC) Tokens**
  - The gold standard for human users in production environments.
  - Users authenticate with an identity provider (like Okta, Ping, Azure AD, or Google), which generates a signed JSON Web Token (JWT).
  - The API server reads the cryptographically signed claims inside the token to discover the username and groups.

- **Service Account Tokens**
  - Short-lived JSON Web Tokens automatically provisioned and mounted into pods.
  - Applications inside the pod use this token as a bearer token to seamlessly authenticate against the API server.
- **Webhook Token Authentication**
  - If the API server doesn't recognize a bearer token, it can delegate validation by sending the token to an external HTTP endpoint.
  - This is frequently used by cloud providers, such as AWS EKS utilizing the `aws-iam-authenticator` webhook to map AWS IAM roles to Kubernetes identities.

### Lab: How Authentication works in Amazon EKS?

- In Amazon EKS, authentication is deeply integrated with AWS Identity and Access Management (IAM).
- Instead of managing static X.509 certificates or a separate identity provider, EKS relies on a _Webhook Token Authentication_ mechanism to securely translate AWS IAM identities into Kubernetes users and groups.

- EKS handles authentication by combining AWS IAM and native Kubernetes RBAC in a highly secure, automated handshake:

```
[ kubectl command ]
       │
       ▼
1. Requests token from AWS STS
       │
       ▼
2. Sends request to EKS Endpoint (with STS token as Bearer token)
       │
       ▼
3. EKS Control Plane calls AWS STS to verify token
       │
       ▼
4. EKS maps verified IAM identity to a Kubernetes username/group via EKS Access Entries
       │
       ▼
5. Kubernetes RBAC authorizes the action
```

#### Mapping IAM Identities with Kubernetes Roles using `EKS Access Entries`

- This is the modern, cloud-native way to manage access.
- It allows you to manage cluster access directly via the AWS EKS Console or AWS CLI/Terraform, entirely bypassing the need to edit configuration files inside the cluster.

- **How it works?**
  - You create an "Access Entry" in AWS for an IAM User or Role.
  - You can either attach AWS-managed policies (like AmazonEKSAdminPolicy) or map it to a custom Kubernetes group name that matches your internal RBAC ClusterRoleBinding.

## 02. Authorization (AuthZ): What can you do?

- Once Kubernetes knows who you are, it checks what you are allowed to do.
- It checks if you have permission to perform the requested action (such as get, create, or delete on a resource like a pod or service).

- While K8s supports multiple authorization modules (like Node and Webhook), **Role-Based Access Control (RBAC)** is the industry standard.

- RBAC uses four fundamental API resources, split by their scope:

| Scope                                                | Role Definition (The Permissions)                                                                                 | Binding (Connecting Identity to Permissions)                                                                                  |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Namespace Scope** (Tied to a specific sandbox)     | **Role**: Defines namespaced actions (e.g., "allow reading pods in the dev namespace").                           | **RoleBinding**: Grants the permissions defined in a Role to a specific user, group, or ServiceAccount within that namespace. |
| **Cluster Scope** (Applies across the whole cluster) | **ClusterRole**: Defines cluster-wide permissions (e.g., "allow reading nodes or secrets across all namespaces"). | **ClusterRoleBinding**: Appoints those global ClusterRole permissions to users or service accounts across the entire cluster. |

## Hands-on Lab: Onboarding an IAM User to Amazon EKS Cluster with Cluster Adminstrator access

In this scenario, we will create a new IAM User named `dev-user-bob` and give him cluster-wide access to deploy and manage applications.

- We need to shift _bob_ user Access Scope from `type=namespace` to `type=cluster`.

- When you apply the `AmazonEKSAdminPolicy` at the cluster scope, Bob gains permissions equivalent to the native Kubernetes admin cluster role.
- This allows him to manage workloads (Deployments, Pods, Services, CRDs) across every existing and future namespace in the cluster.

### Step-XX: (Only if required) Remove the Namespace-Scoped Policy

To prevent conflicting rules and keep your configuration clean, remove Bob's existing namespace-restricted policy first:

```bash
aws eks disassociate-access-policy \
    --cluster-name production-cluster \
    --principal-arn arn:aws:iam::123456789012:user/dev-user-bob \
    --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy
```

### Step-XX: Associate the Admin Policy Cluster-Wide

Now, attach the exact same policy, but change the `--access-scope` to `type=cluster`.

```bash
aws eks associate-access-policy \
    --cluster-name production-cluster \
    --principal-arn arn:aws:iam::123456789012:user/dev-user-bob \
    --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
    --access-scope type=cluster
```

### Step-XX: Testing the Bob's (user) cluster-wide access to EKS

Bob's new permissions apply instantly across the entire cluster:

```bash
# 1. Managing workloads in multiple namespaces
kubectl create deployment web-app --image=nginx -n default
# Output: deployment.apps/web-app created

# 2. Viewing all cluster components
kubectl get pods -A
# Output: Lists all pods across all namespaces successfully.
```

## Hands-on Lab: Restrict an EKS User's Access to a specific Namespace

### Step-XX: Create a Namespace

- Before Bob can access the namespace, it must exist in your cluster.
- If it doesn't already exist, create it as a cluster administrator:

```bash
kubectl create namespace development
```

### Step-XX: (If Applicable) Remove Old Cluster-Wide Access

- If you previously ran the command from the earlier example that gave Bob cluster-wide viewer access, you must first remove that policy to ensure he doesn't maintain overarching privileges:

```bash
aws eks disassociate-access-policy \
    --cluster-name production-cluster \
    --principal-arn arn:aws:iam::123456789012:user/dev-user-bob \
    --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewerPolicy
```

### Step-XX: Associate the Policy with a Namespace Scope

- Now, attach the policy again. This time, we use the `--access-scope` flag to restrict his permissions strictly to the **development** namespace:

```bash
aws eks associate-access-policy \
    --cluster-name production-cluster \
    --principal-arn arn:aws:iam::123456789012:user/dev-user-bob \
    --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewerPolicy \
    --access-scope type=namespace,namespaces=development
```

> [!NOTE]
> If you ever want to give user access to multiple namespaces (like development and staging), you can pass them as a comma-separated list: namespaces=development,staging.

### Testing the Access

- Once configured, Bob's authentication token will behave differently depending on how he scopes his kubectl commands.

- This will `FAIL` (Cluster-wide access denied)

  ```bash
  kubectl get pods -A

  # Output: Error from server (Forbidden): pods is forbidden...
  ```

- This will `SUCCEED` (Namespace access granted)

  ```bash
  kubectl get pods -n development
  # Output: No resources found in development namespace. (Success!)
  ```
