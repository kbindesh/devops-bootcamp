# Kubernetes Key Concepts

## 🎡 01. Kubernetes API

- The Kubernetes (K8s) API is the HTTP REST interface that serves as the single point of entry for managing, configuring, and interacting with a Kubernetes cluster.

- Everything in Kubernetes is an API object like:
  - Pods
  - Services
  - Deployments
- Every action - whether triggered by a user via kubectl, internal cluster components like controllers, or external CI/CD pipelines—is processed as an HTTP request to this API.

## 🧱 02. Core Concepts of the K8s API

The K8s API is structured around standard RESTful principles and treats cluster infrastructure as software resources:

- **HTTP Verbs (CRUD)**
  - The API translates standard actions into HTTP verbs:
    - POST (create)
    - GET (read/list)
    - PUT/PATCH (update)
    - DELETE (destroy).

- **The `Watch` Mechanism**
  - Instead of constantly polling the API for updates, clients can send a GET request with a ?watch parameter.
  - This opens a persistent stream, allowing the API server to push real-time event updates whenever an object changes.

- **Declarative State**
  - You define the desired State of your infrastructure/app in a YAML or JSON file.
  - The API server saves this configuration into storage, and background controllers work continuously to match the cluster's actual state to your desires.

## 🔄 03. How the Kube API Server Processes requests

Whenever a request is sent to the kube-apiserver, it passes through a strict sequential pipeline before changing anything in the cluster:

```
[ HTTP Request ]
       │
       ▼
 1. Authentication  ──► (Who are you? E.g., Certificates, Tokens)
       │
       ▼
 2. Authorization   ──► (What can you do? Checked against RBAC policies)
       │
       ▼
 3. Mutating Webhooks ──► (Modifies/injects defaults into the request)
       │
       ▼
 4. Object Validation ──► (Checks YAML formatting against strict schema)
       │
       ▼
 5. Validating Webhooks ──► (Final security check; can reject the request)
       │
       ▼
 [ etcd Database ]  ──► (State successfully saved to the cluster store)
```

## 📂 04. Structure of the API (Groups and Versions)

- To scale and adapt without breaking older deployments, the K8s API is highly structured into `API Groups` and `Versions`.
- This is why every K8s YAML file requires an `apiVersion` string at the beginning.

### 4.1 Core API vs. Named Groups API

Core Group (/api/v1): Legacy, foundational resources that do not have a group name in their path (e.g., Pods, Services, Namespaces, ConfigMaps).

Named Groups (/apis/$GROUP_NAME/$VERSION): Organized by functionality to make the platform extensible. For example, a Deployment belongs to apis/apps/v1, while a CronJob belongs to apis/batch/v1.

### 4.2 Three Core API Maturity Levels

1. **Alpha** (v1alpha1, v2alpha1, etc.)
   - _Intent_: Early experimental testing and feedback gathering.
   - _Defaults_: Disabled by default. Cluster admins must explicitly use feature gates to activate them.
   - _Deprecation_: Can be completely dropped in the very next release. Recommended strictly for isolated development clusters.

2. **Beta** (v1beta1, v2beta1, etc.)
   - _Intent_: Real-world testing and stabilization. The code is well-tested and considered safe for non-critical workloads.
   - _Defaults_: Enabled by default in most standard Kubernetes distributions.
   - _Deprecation_: Governed by a strict timeline. A Beta API has a concrete lifespan (typically deprecated after 3 releases or 1 year) by which it must either advance to Stable or be removed.

- **Stable** (v1, v2, etc.)
  - Intent: Production-ready features for mission-critical enterprise environments.
  - _Defaults_: Enabled by default and fully optimized.
  - _Deprecation_: If a Stable API is ever deprecated, it will be supported alongside its replacement for a minimum of 12 months or 3 releases (whichever is longer) before removal.

## 🛠️ 05. Extensibility: CRDs

- Custom Resource Definitions (CRDs) are the primary way to extend the Kubernetes API.
- They allow you to define your own custom objects (like Database, User, or FrontendConfig) and treat them exactly like built-in Kubernetes objects such as Pods, Deployments, or Services.

### 5.1 The 2 Core Components of Extensibility

Extending Kubernetes with a CRD requires two separate parts working together:

1. The Custom Resource Definition (CRD)
   - The blueprint.
   - It defines the name of your resource, the API group, and the structural schema (validation rules) using OpenAPI v3.

2. The Custom Controller (Operator)
   - The brain.
   - A continuous loop that watches your custom resources and takes action to make the actual state match your desired state.

Without a controller, a CRD is just a structural data entry in the cluster database (etcd).

### 5.2 How a CRD Works?

When you submit a CRD yaml file to the cluster, the Kubernetes API server dynamically creates a new HTTP endpoint for that resource.

## 06. Different approaches to communicate with Kubernetes API Server

You can communicate with the Kubernetes API Server using _four_ primary approaches, depending on whether you are an administrator using the command line, an application running inside the cluster, or an external automated system:

1. The Command-Line Interface (kubectl)
2. Official and Community Client Libraries (SDKs)
3. Direct HTTP REST API Calls
4. In-Cluster Pod Communication (Service Accounts)

```
+------------------+     (HTTP / REST / JSON)     +--------------------+

|  1. kubectl CLI   | --------------------------> |                    |
+------------------+                              |                    |

|  2. Client SDKs  | --------------------------> |                    |
+------------------+                              |   kube-apiserver   |

|  3. Direct REST  | --------------------------> |                    |
+------------------+                              |                    |

|  4. In-Cluster   | --------------------------> |                    |
+------------------+                              +--------------------+
```

### 6.1 The Command-Line Interface (kubectl)

This is the most common approach for human administrators, developers, and DevOps engineers.

- How it works?
  - It wraps the REST API into human-friendly commands.
- Authentication
  - Automatically looks for configuration files at ~/.kube/config.Key
- Advantage
  - Handles complex tasks like parsing outputs, streaming logs, opening port-forwards, and chunking large lists automatically.
- Best For
  - Manual cluster management, debugging, and simple scripting.

### 6.2 Official and Community Client Libraries (SDKs)

When writing software, operators, or integration tools, you use programmatic SDKs rather than parsing CLI text output.

- How it works?
  - Libraries generate strongly typed code bindings from the K8s OpenAPI spec.

- Supported Languages
  - Official libraries exist for Go (client-go) and Python.
  - Highly reliable community libraries exist for Java, JavaScript, C#, and Rust.Key
- Advantage
  - Provides advanced features like Informers and Reflectors that cache cluster states locally, reducing unnecessary API load.
- Best For
  - Building Custom Controllers, Operators, CI/CD tools, and internal platforms.

### 6.3 Direct HTTP REST API Calls

Because the Kubernetes API Server is essentially a standard REST server, you can bypass all tools and hit it directly.

- How it works?
  - Standard HTTP verbs map directly to cluster actions:
    - GET /api/v1/pods &rarr; Lists pods.
    - POST /api/v1/namespaces/default/pods &rarr; Creates a pod.
    - DELETE /api/v1/namespaces/default/pods/my-pod &rarr; Deletes a pod.
- Authentication
  - You must manually pass a bearer token in the HTTP Authorization header or provide TLS client certificates.
- Best For
  - Lightweight shell scripts (curl), automated webhooks, or languages lacking an updated SDK.

### 6.4 In-Cluster Pod Communication (Service Accounts)

When your application code is running inside a container within the Kubernetes cluster, the communication mechanism changes for security and convenience.

- How it works?
  - You do not use an external kubeconfig file.
  - Instead, Kubernetes automatically mounts a secure token, a CA certificate, and a namespace file into the container at /var/run/secrets/kubernetes.io/serviceaccount/.
- The SDK Handshake
  - Both client-go and the Python SDK have an explicit configuration method called rest.
  - InClusterConfig(): This method tells the library to automatically look for those filesystem paths to authenticate against the internal cluster DNS (https://default.svc).
- Best For
  - Microservices that need to auto-scale themselves, security scanners running inside the cluster, and Custom Operators.

### 6.5 Summary - Comparison of Methods

| Approach    | Setup Effort                  | Performance                   | Best Use Case                       |
| ----------- | ----------------------------- | ----------------------------- | ----------------------------------- |
| kubectl     | Minimal (One-time config)     | Medium (CLI overhead)         | Human administration & debugging    |
| Client SDKs | Medium (Code integration)     | High (Supports local caching) | Building internal tools & operators |
| Direct REST | High (Manual auth/headers)    | High                          | Webhooks & simple curl automation   |
| In-Cluster  | Low (Handled by k8s platform) | High                          | Internal microservices & plugins    |
