# Deploying and Managing Stateless Apps using K8s Deployments

## Deployments - Overview

- A **Deployment** is a kubernetes object which provides us a convenient way to define the desired state application deployment.

- It provides us with a better way of upgrading the underlying instances seamlessly using:
  - rolling updates
  - undoing changes, and
  - pausing and resuming changes as required

- Deployments provide a way to define a desired state for the replica pod.

## Deployment - API specifications

A standard Kubernetes Deployment specification includes four main structural components:

- apiVersion
- kind
- metadata
- spec

### apiVersion & kind

Defines the Kubernetes API version and the type of object.

```yaml
apiVersion: apps/v1

kind: Deployment
```

### metadata

Identifies the Deployment resource.

```yaml
metadata:
  name: <name-of-the-deployment>

  labels: <key-value pairs used to organize and select groups of objects>

  namespace: <namespace>

  annotations:
    - <annotation>
```

### spec (deployment controller rules)

Defines the behavior and rules for the Deployment.

```yaml
replicas: <number-of-identical-desired pods (e.g. 3)>

# This must match the labels in your Pod template
selector: <label query that tells the Deployment which Pods to manage>

# Defines how the Deployment transitions to a new version
strategy:
  - type: RollingUpdate/Recreate

# default strategy is "RollingUpdate", updates Pods sequentially without downtime).

# "Recreate" strategy terminates all old Pods before creating new ones
```

### template (the pod specifications)

- Defines the actual Pods that the Deployment will create.
- This section nests its own `metadata` and `spec`.

```yaml
template:
  metadata: Contains labels for the Pods
  spec:
    containers: Array of containers running inside the Pod
      name: Container name
      image: The container image to run (e.g., nginx:latest)
      ports: The container port to expose
        containerPort: 80

      # Compute restrictions
      resources:
        limits: maximum CPU and Memory the container is allowed to use

        requests: guaranteed minimum CPU and Memory allocated to the container

      # Environment variables
      env: environment variables injected into the container

      volumeMounts: mounts persistent storage volumes or ConfigMaps into the container
    # Storage for container
    volumes: Defines the physical storage disks or configuration data made available to the Pod
```

## Lab: Deploy an Application (nginx) with 3 replicas

### Create a Deployment manifest

- Write a YAML definition for Deployment object:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
    labels:
      app: nginx
  spec:
    containers:
      - name: nginx
        image: nginx:latest
        ports:
          - containerPort: 80
```

The following attributes are important to help you understand the preceding YAML definition:

- `spec.replicas` gives us the number of replica pods
- `spec.template` is the template pod descriptor that defines the pods that will be created
- `spec.selector` is the deployment that will manage all pods whose labels match this selector

- Deploy the application using Deployment object:

```bash
kubectl apply -f deployment.yaml
```

```bash
# List all the existing Deployment objects present in default namespace
kubectl get deployments
OR
kubectl get deploy

# Describe deployment details
kubectl describe deployment <deployment_name>
kubectl describe deployment deployment.yaml
```

### Live edit a Deployment object

```bash
kubectl edit deployment <deployment_name>

# You may revise the replica count or image then save the file and quit using wq!
```

### Delete a Deployment

```bash
kubectl delete deployment <deployment_name>
```

## Lab: Performing Rolling updates on Deployment

- Rolling updates provide a way to update a Deployment to a newer version more effectively and efficiently.
- This way, you can update Kubernetes objects such as replicas and pods gradually with nearly zero downtime.

- There are 2 native deployment update strategies:
  1. Recreate
  2. Rolling update (default)

### Create a deployment manifest

- Create a new yaml file, say **deployment.yaml** for deploying nginx application with 3 replicas:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
    labels:
      app: nginx
  spec:
    containers:
      - name: nginx
        image: nginx:latest
        ports:
          - containerPort: 80
```

- Apply the above created yaml manifest, deployment.yaml:

```bash
kubectl apply -f deployment.yaml
```

### Update the Application's container image (from nginx:latest to nginx:1.25.5) by editing the manifest:

- Open the `deployment.yaml` file in edit mode and update the _image_ property of the Pod container:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
    labels:
      app: nginx
  spec:
    containers:
      - name: nginx
        image: nginx:1.25.5
        ports:
          - containerPort: 80
```

- Deploy the updated deployment manifest:

```bash
kubectl apply -f deployment.yaml
```

### Verify the deployment image update:

```bash
# Describe deployment to check the image update
kubectl describe deployment app-deployment
```

### Rollback a Deployment

- To rollback any application back to any revision, you can use `kubectl rollout` command.

- Rollback allows us to revert our application to a previous state (deployment) seamlessly.

```bash
# To perform a deployment rollback to immediate previous revision
kubectl rollout undo deployments <deployment_name>

kubectl rollout undo deployments app-deployment

# To perform a deployment rollback to a particular revision
kubectl rollout undo deployments app-deployment --to-revision=2

# To verify the rolled back image (prev)
kubectl describe deployment <deployment_name>
```

### Set the Deployment _Change cause_

- To set the Deployment change cause, you can add `kubernetes.io/change-cause` annotation.

```bash
# To get more info
kubectl annotate --help

# Deploy Application
kubectl apply -f deployment.yml

# To capture the change cause using annotation
kubectl annotate deployment $DEPLOYMENT_NAME kubernetes.io/change-cause="image updated to nginx 1.28"

# View Deployment history (revisions) with change cause
kubectl rollout history deployment $DEPLOYMENT_NAME
```
