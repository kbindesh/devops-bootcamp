# Auto-scaling Workloads in Kubernetes

- Auto-scaling means allowing the cluster automatically adjust its resources based on how much work it needs to do.

## Types of Auto-Scaling in Kubernetes

Kubernetes relies on three primary methods to scale. They work together like a well-oiled machine.

**1. Horizontal Pod Autoscaler (HPA) – "Scaling Out"**

- Increase/Decrease Pod Quantity

**2. Vertical Pod Autoscaler (VPA) – "Scaling Up"**

- Increase/Decrease Pod Size

**3. Cluster Autoscaler – "Infrastructure Scaling"**

- Infrastructure Capacity (Cluster level)

```
       ┌─────────────────────────────────────────┐
       │         Your Application (Pods)         │
       └────────────────────┬────────────────────┘
                            │
            Is CPU/Memory high? OR Are there custom metrics?
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
  [ HPA: Scale Out ]               [ VPA: Scale Up ]
  Add more copies (Pods)          Make existing Pods bigger
            │
  Are Node resources full?
            │
            ▼
 [ Cluster Autoscaler / Karpenter ]
 Add more physical/virtual servers (Nodes)
```

### Horizontal Pod Autoscaler (HPA)

- The HorizontalPodAutoscaler scales the number of Pod replicas up or down in response to real-time demand.
- It is the most commonly used scaling method for stateless workloads.

- _How it works?_
  - A control loop (running by default every 15 seconds) queries the Metrics Server to check metrics against target thresholds.

- _Triggers_
  - Standard resource usage (CPU or memory)

- _Example_
  - If your target CPU is set to 60%, and an unexpected traffic spike pushes utilization to 90%, HPA provisions additional Pods to distribute the load.
  - Once traffic drops, it automatically downsizes the replica count to avoid wasting resources.

### Vertical Pod Autoscaler (VPA)

The Vertical Pod Autoscaler adjusts the CPU and memory resource requests/limits of existing containers instead of adding more Pod copies.

- *How it works?*
  - The VPA analyzes historical and real-time usage data.
  - If a Pod regularly runs out of memory (OOM), the VPA recommends or applies a larger resource pool profile.

- *Limitation*
  - Traditionally, applying VPA updates requires recreating/restarting the Pod.

`Note`: In-place vertical scaling is stable as of modern Kubernetes releases, though full native VPA integration for doing this without a restart continues to mature.

> [!WARNING]
> Do not run _HPA_ and _VPA_ together on the exact same metric (like CPU usage). They will conflict - one will try to spin up new Pods while the other tries to make the current Pods physically larger.

### Cluster Autoscaler (CA) & Karpenter

When your Pod autoscalers (HPA/VPA) request resources that the underlying physical servers (nodes) cannot accommodate, your Pods sit in a Pending state. Cluster-level scaling steps in to manage node infrastructure capacity.

- *Cluster Autoscaler (CA)*
  - Automatically spins up new worker nodes from your cloud provider's node pools when Pods fail to schedule due to resource shortages. 
  - It safely de-provisions nodes when they remain underutilized for too long.

- *Karpenter*
  - A high-performance, open-source alternative to CA. 
  - Instead of relying on rigid cloud node groups, Karpenter evaluates the unfulfilled Pod requests directly and instantly launches the optimal, right-sized EC2/compute instances, drastically reducing scaling latency.

### Event-Driven Autoscaling (KEDA)

**Kubernetes Event-driven Autoscaling (KEDA)** acts as a metrics adapter to scale based on external event data.

  - *Triggers*
    - Queue depths (e.g., RabbitMQ, Apache Kafka), database rows, or incoming HTTP request rates.
  - *Scale to Zero*
    - Unlike native HPA, KEDA can scale your deployments completely down to 0 replicas when there are no events to process, and instantly bring them back to life when an event arrives.

### Summary Comparision

| Scaling Method | What It Scales?                 | Best Used For                                               | Key Metric Sources                   |
| -------------- | ------------------------------ | ----------------------------------------------------------- | ------------------------------------ |
| **HPA**            | Number of Pod replicas         | Stateless microservices, web apps                           | Metrics Server (CPU/RAM)             |
| **VPA**            | Sizing of a single Pod         | Stateful sets, databases, heavy single-stream jobs          | Historical usage profiles            |
| **CA / Karpenter** | Number of Cluster Nodes        | Core infrastructure scaling when nodes fill up              | Un-schedulable/Pending Pod statuses  |
| **KEDA**           | Pod count (via custom metrics) | Event-driven architecture, messaging queues, CRON schedules | Kafka, RabbitMQ, AWS SQS, Prometheus |

## Lab: Configure auto-scaling for an Application using HPA (Horizontal Pod Autoscaler)

Let's say you run an e-commerce website. Suddenly, a celebrity tweets about your product, and traffic spikes. Here is how you set up HPA to handle the rush.

### Develop Application manifests (Deployment, ClusterIP service)

### Create the Auto-Scaler (HPA) rule HPA manifest

- *Scenario*
  - If the average CPU usage across my apps goes over 70%, add more pods to the pool, up to a maximum of 5.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: store-scaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: online-store
  minReplicas: 2
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```
